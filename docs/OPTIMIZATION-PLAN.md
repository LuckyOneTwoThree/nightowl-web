## 二、真实问题（3 项，均已实机验证）

### P1 · tbd 场次的时间公布滞后 —— 最该修

**现象**：联赛官方提前 2–4 周公布精确开球时间后，应用仍显示「时间待定」，直到比赛踢完。

**证据链**：

1. **53.9% 场次（1023 场）是 tbd 占位**，且 **108 / 108 个 tbd 轮次整轮共用一个占位时间**：
   ```
   BL 第5轮 9 场 → 占位时间全部是 2026-10-11T02:00
   BL 第6轮 9 场 → 占位时间全部是 2026-10-18T02:00
   ```
   而一轮 9 场实际跨周五 / 周六 / 周日**三个不同的日子**。

2. **保鲜只按占位日查一天**。`activeSyncTargets()` 用 `ts(m.t)`（占位时间）算查询日期，
   每个 tbd 轮只生成 **1 个 `dates=YYYYMMDD`** 查询：
   ```
   模拟 BL 第5轮占位日前 1 天 → 查询日期: BL → 20261010（仅 1 天）
   ```
   ESPN 按精确日期返回，**非占位日的场次根本不在响应里**，`planPatches` 里
   `MATCH_WINDOW_DAYS=4` 的邻近度兜底无从生效（事件没被拉到，谈不上匹配）。

3. **副源救不了时间**。openfootball 拉整季文件（能覆盖所有日期），但时间口径是
   **联赛当地墙钟、无时区**，适配器显式标记 `kickoffTrusted: false`，合并层
   `timePick = sorted.find(e => e.kickoffTrusted && e.kickoff)` 不会采用它。
   且 openfootball **不覆盖欧冠**。

4. **已踢完的 tbd 场能被救回，没踢的不能**——模拟验证：
   ```
   openfootball 单源事件（done + 有比分）
     → state='done', patch.sc 生效 → 走 (state==='done' && patch.sc) 分支 → tbd=false ✓
   未开球场次 → 无比分 → 两个 tbd 清除分支都不命中 → tbd 永久挂着 ✗
   ```

**影响面**：1023 场 tbd 中所有「官方已公布时间、尚未开球」的场次。
用户在赛程页和「本周规划」里看到的是占位时间而非真实时间，背包与雷区的档位计算
全部基于占位值（虽然 `st='sched' && tbd=true` 会被算法过滤，但用户浏览层面看到的是错的）。

**根因**：tbd 占位时间只是「这一轮通常在几点踢」的猜测，保鲜模块把它当成查询坐标，
却没考虑一轮跨多天。

**修复方案**（两选一，推荐 A + B 组合）：

- **A. tbd 场按「轮次窗口」展开查询日期**（改 `activeSyncTargets`，小而稳）
  - tbd 场不按单日，而是展开为占位日 **±3 天**的日期集合（覆盖一轮的周五~周日）
  - 代价：每个 tbd 轮从 1 次请求变 7 次。常态同步窗口内 tbd 轮通常只有 1~2 个，
    增量约 6~12 次请求，可接受（现有单次同步约 15 秒，串行 + 200ms 间隔）
  - 收益：官方一公布就能拿到真实时间，tbd 立即转正

- **B. 给 openfootball 加时区换算，升级为可信时间源**（改 `openfootball.js`，收益最大）
  - 按联赛补 UTC 偏移：PD/SA/FL/BL 用 CET/CEST（+1 / +2，需区分夏令时），
    PL 用 GMT/BST（+0 / +1）
  - 换算成北京墙钟后置 `kickoffTrusted: true`
  - 收益：openfootball 一次请求拿整季，**所有 tbd 时间一次性转正**，且不再依赖 ESPN 的
    按日查询；ESPN 仍保留为主源做交叉校验
  - 风险：夏令时换算错一天就是整体偏移，**必须配回归测试**（见验收）

- **暂不建议**：改 ESPN 为日期范围查询（上游对日期范围返回 400，`sources/index.js` 注释已记录）

**验收方式**：
- 新增 `tools/test-tbd-sync.mjs`：构造一个 tbd 轮（多场、跨三天），断言修复后
  生成 ≥3 个查询日期 / openfootball 时间被采信且 tbd 清除
- 联网实测：`npm run sync:scores` 后 tbd 场数应显著下降（当前 1023）
- 现有 `npm run test:scores`（19 项）必须全过——尤其「done 必有比分」「st 取值域」两条铁律

### P2 · 欧冠淘汰赛 45 场全缺

**现象**：UCL 只有联赛阶段，淘汰赛阶段完全缺失。

**证据**：
```
UCL 场数: 144    轮次: [1,2,3,4,5,6,7,8]    末场: 2027-01-28
```
- 144 场是**完整的新制瑞士轮联赛阶段**（36 队 × 8 轮 ÷ 2 = 144），这块没问题
- 缺口是淘汰赛：淘汰赛附加赛 16 + R16 16 + QF 8 + SF 4 + 决赛 1 = **45 场**
- UCL 的 tbd 率是 **0%**（时间全已知），但 2027-01-28 之后欧冠就从应用里消失了
- 欧冠凌晨场正是「值不值得熬」的**核心场景**，且赛程最后阶段（淘汰赛）看点最密集

**根因**：数据迁移（`tools/migrate-data.mjs`）时上游欧冠数据只含联赛阶段。

**修复方案**：
- 淘汰赛对阵需等 2027-01 抽签后才能确定，当前**无法补全赛程**
- 可做的是**接管路径**：在 `activeSyncTargets` / ESPN 适配器里，UCL 的 targets 不依赖
  本地 fixtures 是否存在——ESPN 的 `uefa.champions` scoreboard 会自带淘汰赛赛程
- 具体做法：sync 时对 UCL 增加一轮「按月扫描」而非仅按本地已有场次扫描，
  拉到本地没有的新对阵 → 走 `unmatched` 报告 → 由脚本决定是否纳入
- **注意**：这会触及「数据只走脚本、不手工编辑」的铁律，新增场次必须走迁移脚本而非手改 JSON

**验收**：`node tools/check-sources.mjs` 健康检查里 UCL 覆盖度提升；2027-01 后 UCL 不再空窗。

### P3 · 直播源抓取器的正则脆弱性

**现象**：赛程抓取依赖 3 个强耦合的 HTML 正则，站点一改版全部失效。

**证据**：
```js
class="[^"]*group-game-item[^"]*"[\s\S]*?href=['"](\/live\/(\d+)\/play)['"]...
class="team-name"[^>]*>([^<]+)
class="[^"]*category-game-time[^"]*"[^>]*>([^<]+)
```
- 三处正则同时依赖具体的 CSS 类名（`group-game-item` / `team-name` / `category-game-time`）
  与 DOM 层级（`<a>` 包裹 + `group-game-item` 容器）
- 现有容灾只覆盖**网络层**（4 个镜像域名轮询），**不覆盖结构变更**：站点改一次类名，
  四个镜像全部返回 0 条，且因为 `fetchSchedule` 不抛错（只是空数组），
  界面会静默降级成「本场暂无直播线路」——用户分不清是没匹配还是抓取挂了
- `getLiveSourcesForMatch` 已把 `scrapeError` 显式区分出来（镜像全挂时），但
  「结构变了、解析到空数组」这一支不会触发它，是**静默失败**

**修复方案**：
1. **加结构性探活**：`fetchSchedule` 解析后若 `games.length === 0` 但 HTML 非空，
   判定为「解析失败」而非「今天没比赛」，抛错走 `scrapeError` 分支，让界面明确提示
2. **正则降级链**：主正则失败时尝试 1~2 套备选结构（或退化为「只取 `/live/\d+/play`
   链接 + 后续逐房间解析」的粗粒度模式）
3. **离线回归**：在 `tools/test-scraper-match.mjs` 里存一段真实 HTML 快照，
   断言解析出的场次数与队名，改版时测试先红

**验收**：`npm run test:scraper-match`（22 项）与 `npm run check:scraper`（7 项）全过。

## 三、已核实排除项

**`activeSyncTargets` 的日期口径（原「待核实」，已联网验证为正确）**

```js
const d = new Date(t);              // t = ts(m.t) 已减 8 小时
const ymd = `${d.getUTCFullYear()}...`;   // 再取 UTC 分量
```
对凌晨场次，`2026-09-19T03:00`（北京）经 `ts()` 减 8h 后是 `2026-09-18T19:00Z`，
取出的 ymd 是 `20260918`。**这正是 ESPN `dates=` 参数要的日期**——实测：

```
对照 BRE vs CHE（北京墙钟 2026-09-19T03:00）
【减8h口径】 dates=20260918 → 1 场, 2026-09-18T19:00Z "Chelsea at Brentford" → 命中 ✓
【北京墙钟口径】 dates=20260919 → 5 场，无对照场次 → 不命中
```

结论：ESPN 按事件 **UTC 日期**过滤，当前实现「ts 减 8h → 取 UTC 分量」与之精确一致。
看似的 off-by-one 是刻意设计，**不是 bug，无需改**。

验证脚本：`node tools/verify-espn-dates.mjs`（联网）。

## 四·五、深度复审（2026-09-17）→ ✅ 无遗留问题

对上述全部优化逐项复查「是否引入新 bug」，共查出 **4 处**，全部修复并复测：

### 复审发现 1：tbd 展开放大积压场景的请求量（P1-A 的副作用）

**问题**：`activeSyncTargets` 的 `t <= future48h` **没有下界**——任何仍是 `sched`
的场次只要开球时间不超过「未来 48 小时」都会被查询。稳态（每日同步）下已完赛场次
早被标记 `done`，积压只有近 48 小时的 7 个日期，没问题。

但用户关闭应用数周后重开，整段未同步的 `sched` 场次会全部成为积压。此时我引入的
tbd 展开把**每个积压 tbd 场次从 1 个请求放大成 7 个**：实测把 `now` 快进到
2027-05-29（积压场景峰值），请求数 **845**，改动前约 38。

**修复**（`server/scores.js`）：展开加近期待守卫——只在占位日仍可能覆盖真实比赛日时
展开：

```js
if (m.tbd && t >= nowTs - TBD_EXPAND_DAYS * 86400000) { ...展开... }
```

ESPN 在开球前数日就公布真实时间，此时占位日在未来或临近；占位日已过去很久仍为 tbd
的场次，展开窗口早已整体落在过去，再查也查不到，只是把 1 个请求永久放大成 7 个。

**边界用合成数据精确验证**（6 个合成场次，覆盖 3 天整/差 1 分钟/深积压/未来）：
3 天整（含）展开 7 个日期、3 天差 1 分钟不展开、过去 4 天的 tbd 只贡献 1 个日期，
并集 11 个日期与手算完全一致。**真实近场景不受影响**：BL 第 5 轮占位日临近时
仍展开出 `20261007–20261013` 共 10 个日期。

**效果**：稳态仍是 **7 个请求/次**，积压峰值 845 → **247**。

### 复审发现 2：openfootball 对 UCL 的空请求（P2 的副作用）

`uclWeeklyTargets` 把 UCL 塞进 targets，但 openfootball 只覆盖五大联赛
（`LEAGUES` 里没有 UCL），每次同步白跑一个必然为空的请求。
**修复**（`server/sources/index.js`）：`units()` 开头加
`if (!openfootball.LEAGUES[league]) return [];`。
**实测**（网络层按 URL 计数）：openfootball UCL 请求 **1 → 0**。

### 复审发现 3：探活阈值可能误报（P3 的自身风险）

原判据「HTML 含 ≥1 个 `/live/` 链接却解析出 0 条」在**无比赛日**可能误触发——
页脚的重播链接也算。**修复**（`server/scraper.js`）：阈值提到 **≥3** 个直播链接，
更贴近「整页有大量场次入口却一条都没解析到」的改版特征。
`test-scraper-parse.mjs` 新增反例：3000 字符填充 + 1 个页脚链接的「无比赛日」页面，
断言**不触发**探活（该脚手 22 项）。

### 复审发现 4：删除已死的危险函数

openfootball 改用 `tz.mjs` 后，`normalize.js` 的 `localPartsToWall` 再无调用者，
而它保留着「缺时间默认 00:00」的危险语义（正是 P1-B 修复的那个造假口径）。
**删除**并留注释说明为何不能重新引入，防止被「顺手加回来」。
