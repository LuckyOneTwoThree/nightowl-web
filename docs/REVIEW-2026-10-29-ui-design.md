## 一、先说结论

这个项目的设计系统纪律是**真材实料**的，不是文档摆设。我特意去证伪了几件事，都没证伪成功：

| 检查项 | 结果 |
| :--- | :--- |
| Tailwind 原生色泄漏（`emerald-500` 之类） | 未发现 |
| 任意字号 `text-[Npx]` | 未发现 |
| 任意圆角 `rounded-[Npx]` | 未发现（桌面） |
| 任意 `z-[N]` | 未发现 |
| 文本 token 对比度 | `text-muted` 6.64:1、`text-faint` 5.80:1、`accent` 9.81:1（均以 card 为底；faint 在 raised 5.37、press 4.68） ✅ **但 `text-live` 两处失守**（§1.1） |
| `test:contrast` / `check:render` | **32/32、52/52** 通过（已补 live 与变量引用断言；§1.1、§十一） |

**所以主线问题不在「执行不严」。** 但先说两个**看得见的真 bug**，它们比任何风格建议都该先修。

## 1.1 两个看得见的 bug

### ① 预算滑杆是浏览器原生蓝色

`src/components/WeekView.jsx:185`：

```jsx
className="mt-2 w-full accent-[rgb(var(--resource))]"
```

而 `src/index.css:149` 定义的是 `--resource: #45bfae`（**hex**），`--resource-rgb: 69 191 174`（才是 `rgb()` 用的三元组）。

于是生成的 CSS 是 `accent-color: rgb(#45bfae)` —— **非法值**，浏览器直接忽略，滑杆回退成 UA 默认的**蓝色**。

这不是风格问题，是「睡眠额度」这个**全站独占 resource 色**的核心控件，实际渲染成了一个外来色。直接违反铁律 1。

**修**：`accent-[rgb(var(--resource-rgb))]`。一行。

> 顺带建议给 `test:contrast` / `check:render` 加一条「所有 `rgb(var(--…))` 引用的变量必须是 `-rgb` 三元组」的静态断言 —— 这类 bug 截图里很难一眼看出（蓝色滑杆看着也"挺正常"），只能靠检查拦。

### ② `text-live` 红字在两个常见底色上低于 WCAG AA

`--live: #e2564f` 在小字（11–12px）场景下：

| 组合 | 对比度 | 出处 |
| :--- | :--- | :--- |
| `text-live` on `bg-live/15` | **4.07:1** ❌ | `HeroCard.jsx:182-185`（11px 分钟数）、`atoms.jsx:109`（Chip live） |
| `text-live` on `surface-raised` | **4.39:1** ❌ | `MatchRow.jsx:59-60,126`（live 行 hover 后的 12px 红字） |
| `text-white` on `danger`（hover） | **2.75:1** ❌ | `TopBar.jsx:45` |
| `text-faint` on `surface-press` | 4.68:1（余量仅 0.18） | 大量 `text-2xs text-text-faint` |

我第一遍自己算 muted/faint/accent 时都过了，**漏了 live** —— 原 `test:contrast` 的 23 条也没覆盖这几个组合，所以"测试通过"给了一个假的安全感。核查后已把 live 与变量引用断言补进 32 条门禁。

**修**：把 `--live` 提亮到 `#e86a62`，并把 live tint 从 15% 降到 10%（`#ee6b63` 在 live-10 raised 上仍只有 4.38:1）（或改 chip 底色 / 行 hover 面），并把上述四组加进 `test:contrast`。

**回到主线。** 下面三件事不是靠继续收紧 token 能解决的：

### 主线一 · 排版层级塌缩了，密度却没换来信息

桌面端显式字号类共 360 处，其中 `text-2xs`(11px) 185 处 + `text-xs`(12px) 128 处 = **87% 落在 11–12px**；`text-base` 以上共 24 处。层级实质上只有两档。

讽刺的是同一个屏幕里还空着大片：「看点与代价」面板的左栏在"黄金修仙档·次日注意补觉"之下**空了约 300px**（四张截图一致复现，`.shots/review-1039/tonight-1440-dark.png` 等），右栏「直播线路 + 官方平台」卡内部约 **50% 是空白**。

> **小字 + 大片空白同时存在**，说明问题不是"信息太多放不下"，而是**该大的地方没大、该合并的地方没合并**。
> 设计规范写的是"极高信息密度"，实际做成了"极小字号 + 低填充率"。

### 主线二 · 核心决策指标「夜猫指数」没有可读刻度

这是本轮**最伤产品的一条**。

- 同一屏里既有 `指数 2.5`（今夜无必看、弱场），也有 `指数 27.2`（利物浦 vs 阿森纳）、`13.2`。**同一个名字、同一个量纲、相差一个数量级。**
- Hero 旁边还并排放着 `★☆☆`（1–3 星，来自 `evaluate().star`），与指数是**两个不同的质量信号**，却长得像同一个东西的两种表达。
- 弱夜文案写"指数低于 5.0 推荐线"，暗示刻度是 0–5 量级；但周计划里赫然是 27.2。
- `heroTierOf()` 的阈值是 5 / 15（`src/core/engine.js:166`），说明分布是长尾的（多数 2–5，少数 15+）。

**用户没法回答"2.5 是差还是普通"** —— 而这恰恰是产品承诺的第一个问题「今晚看哪场 / 值不值得熬」。

### 主线三 · 屏幕空间的分配与产品承诺是倒置的

README 承诺回答五个问题，按重要性排序：

| # | 产品承诺 | 实际拿到的屏幕空间 |
| :--- | :--- | :--- |
| 1 | 今晚看哪场 | 左栏 Hero + 列表（25% 的一部分） |
| 2 | 值不值得熬 | 情报面板「看点与代价」tab（75% 的一部分，且左栏空 40%） |
| 3 | 有没有更划算的替代场次 | 「同开球其他 N 场」折叠项，在左栏**最底部** |
| 4 | 这周能承受几场 | **整个周计划挤在约 25% 左栏**，右栏约 75%（1440）/ 70%（1120） 仍在显示单场比赛 |
| 5 | 双方后续赛程 | 「关联赛程」**二级 tab**，需点进去 |

而占空间最大的是「直播线路 / 官方平台」—— 这是**执行层**信息（怎么播），不是**决策层**信息（看不看）。

一句话概括：**产品说"帮你少熬几场"，UI 却把最多的地方给了"怎么播"。**

## 二、设计稿与交付物的落差（解释了很多"为什么空"）

`ui/stitch_modern_ui_design_system/` 里的原始设计稿是**电竞演播台**风格：阵型透视图、xG 预期进球、控球率、传球精度、生物节律诊断、咖啡因窗口、认知负荷、ROI 仪表盘。

而 `ui/UI设计规范与视觉设计系统.md §五` 明令禁止展示这些（无数据，"严禁编造"）。**这个决定是对的** —— 数据诚实是这个产品的资产。

但代价是：**面板是按设计稿的"假数据密度"定的尺寸，真实数据撑不满。** 阵型图没了，那 300px 就空着；战术卡没了，右栏就只剩一行线路 + 6 个 chip。

> 同时 `页面状态机与交互细节指南.md §七` 自己写着：
> **"设计稿目前只产出了『高光卡』一态。标准卡 / 弱化卡 / 无球日三态需补视觉稿。"**
>
> 也就是说 **当前快照约 41% 的弱夜（指数 < 5）从来没有被设计过**，现在是把高光卡压缩后硬凑的。
> 截图里那个"今夜无必看 ★☆☆ / 01:30 / S2 2.5h / 查看赛前情报"的卡片，确实像个被压扁的半成品。

**这三条主线是同一件事的三个面：按数据实际能提供的信息量重新分配空间，而不是继续往设计稿的框里塞。**

## 三、视觉系统层：token 的"声称"与"事实"

### 3.1 文本四档实际只有三档（桌面 + 移动同病）

| Token | 桌面 | 移动 | 问题 |
| :--- | :--- | :--- | :--- |
| `text-secondary` | `#bfc8d6` | `#BFC8D6` | — |
| `text-muted` | `#94a0b2` | `#94A0B2` | 与 faint **几乎同色** |
| `text-faint` | `#8a95a6` | `#8A95A6` | 每通道仅差 ~10 |

`--text-muted` 与 `--text-faint` 在暗底上的对比度是 6.64:1 vs 5.80:1 —— 都合格，但**彼此不可分辨**。规范宣称"文本四档"，实际是三档。

移动端更严重：这两个 token 在同一批文件里被混用于同一种"去强调"语义（`match/[id].tsx` 16/11、`plan.tsx` 11/13、`me.tsx` 12/12，全仓 84/86 次），结果弱文本一片灰，层级立不起来。

**建议**：要么合并成一个 `text-subtle`（承认只有三档），要么把 faint 压到 `#6b7686` 一线、真正拉开一档。**不要保留两个数着玩的 token。**

### 3.2 字号档位命名跨端不一致

同一批像素尺寸，两端叫不同的名字：

| 尺寸 | 桌面（`tailwind.config.js:27-36`） | 移动（`theme.ts:60-72`） |
| :--- | :--- | :--- |
| 11px | `2xs` | `xs`（原 `xxs`/`xs` 同值，已合并） |
| 12px | `xs` | `sm` |
| 13px | `sm` | `md` |
| 15px | `base` | `base` |

移动端原 `fontSize.xxs` 与 `xs` 都是 11 —— **一个伪档位**。核查后已合并为 `xs`；现在 `xs/sm/md/base` 与桌面尺寸一致，但命名仍不同于桌面的 `2xs/xs/sm/base`。

**建议**：两端共用一套档位名（`2xs/xs/sm/base/lg/xl/2xl/display`），尺寸与命名都对齐；把 mobile 的 `xxs`/`xs` 合并。

### 3.3 字重不体系

- 移动端：`800` 用了 23 次（在 400/500/600/700 体系之外，`index.tsx:608,766`、`match/[id].tsx:1419` 等），而 `400` 一次都没用。
- 桌面端：400/500/600/700 规范使用。

两端对同一批中文文案的字重策略不一样，视觉重量明显不同（移动偏胖）。

**建议**：移动端回归 400/500/600/700，禁用 800；正文回落 400。

### 3.4 一处死类

`src/components/SplashScreen.jsx:158` 的 `sm:text-4xl` —— `theme.fontSize` 里没有 `4xl`，这个类**不生成任何 CSS**，大屏下标题实际停在 `text-3xl`。已移除死类；若未来要大屏标题，改用 `text-display`。

### 3.5 字体资产：未用字重与中文字体回退

`public/fonts/` 原 320KB；核查后删除 Hanken 未用字重，现 212KB：

| 字体 | 体积 | 实际用量 |
| :--- | :--- | :--- |
| JetBrains Mono | 125KB | `font-num` **100 处** ✅ 值 |
| Be Vietnam Pro | 40KB | 默认 body ✅ |
| Hanken Grotesk | **34KB（仅 600）** | `font-headline` **仅 2 处**（`Onboarding.jsx:100`、`SettingsDrawer.jsx:191`），且都是 `font-semibold`；400/500/700 已删除 |

`hankengrotesk-400/500/700.woff2` 共 104KB 原为**死重量**，已删除。

更关键的是：**这是一个中文界面，中文没有任何 webfont，全靠系统回退**（`src/index.css:8-9` 注释自陈）。于是：

- 三套拉丁字体只影响数字与 `ARS`/`MCI`/`Ctrl K` 这类缩写；
- 真正决定观感的中文字形，在 macOS 上是 PingFang SC，在 Windows 上是微软雅黑 —— **设计是在 macOS 上调的，而 `dist:win` 是主要发布目标**；
- 叠加"87% 字号在 11–12px"，Windows 上微软雅黑的小字会明显发糊。

**建议**：
1. 砍掉 Hanken Grotesk 的 3 个未用字重（立省 104KB），或干脆删掉这门字体；
2. 把 11px 元信息在 Windows 上的可读性当成一条硬验收（换一台 Win 机器看，或至少把关键元信息回到 12–13px）；
3. 长期：考虑子集化 CJK webfont（思源黑体子集），彻底摆脱系统字体差异 —— 但这是一笔不小的体积投入，可延后。

### 3.6 `warn` 语义泄漏

规范铁律写着 warn/danger 是"系统级异常"，"严禁用于睡眠档位"。这条守住了。但 warn 现在同时承担三件事：

- 「雷区」（`今晚列表` 每行都挂，1440 下 4 行 4 个）—— 是**避坑提示**
- 「同时开球 (5)」（周计划）—— 是**排期约束**，不是警告
- 德比弱警示、聚合源延迟 —— 规范定义的本义

**当每一行都是黄色警告时，警告就失效了。** 而「同时开球」用警告三角形表达，属于语义错配（它其实是个"只能选一个"的选择题）。

**建议**：把"同时开球"降级为中性信息胶囊（不带 ⚠），把「雷区」从"每行都挂"改成只在真正高风险（如 S3+ 且指数低于线）时出现，或收进行首的小图标 + hover。

### 3.7 金色（accent）用量超出"关键决策"的克制线

`index.css:96` 的纪律写着"一屏之内强调元素不超过一个"。实际：

- 顶栏「待录 1 场」计数徽章是**实心金**
- 移动端 accent 用了 85 处（tab 激活、日期激活、关注点、能量条都用金）

计数徽章用实心金，是把"待处理数量"抬到了与"今晚之选"同级。**建议**：实心金只留给主 CTA 与选中态；计数类用描边/柔金底（`surface-accent`）。

### 3.8 token 纪律的漏网（都发生在"高频"组件上）

铁律守住了大头，但漏网的集中在**用得最多的组件**，所以观感影响不小：

| 类型 | 位置 | 问题 |
| :--- | :--- | :--- |
| **原生中性色造中间表面** | `PlayerStage.jsx:933` `bg-white/[0.08]`、`Player.jsx:224` `bg-black/70`、`MatchCanvas.jsx:92-93`、`SplashScreen.jsx:176`、5 处遮罩 `bg-black/6x-7x` | 规范说"不允许组件自造中间色"，但缺 `--scrim` / `--overlay` token，只能手写 |
| **原生阴影** | `shadow-sm`×3（`TopBar.jsx:115`、`IntelPanel.jsx:193`、`WeekView.jsx:296`）、`shadow-2xl`（`PlayerStage.jsx:856`）、`shadow-inner`、`shadow-lg` + 4 处任意 shadow | 规范只有 `shadow-card` / `shadow-pop` 两档 |
| **已废除的发光阴影** | `SettingsDrawer.jsx:455` `shadow-[0_0_12px_rgba(245,185,66,0.25)]` | `index.css:190` 明写"发光类阴影已废除" |
| **过渡时长** | `duration-150/200/300/500/700` 共 10 处，**含 `atoms.jsx:244,262` 的 Button/IconButton**（全站最高频） | 规范三档 120/180/280ms |
| **装饰性上色（违铁律 2）** | `HeroCard.jsx:24` TeamAura `blur-3xl` 主队色光晕、`MatchCanvas.jsx:85,89` 主客色分屏渐变 | "颜色只表达语义，不做装饰性上色" |
| **`font-num` 渲染中文** | `MatchCanvas.jsx:125` 用等宽体渲染「延期」 | 违 `tailwind.config.js:117` 自己写的"mono 不用于中文正文" |
| **accent 透明度 15 档** | `/5 /8 /10 /12 /15 /20 /25 /30 /40 /45 /50 /55 /60 /70 /80` | 语义色透明度应有刻度 |

**建议**：补 `--scrim` / `--overlay-1` / `--overlay-2` 三个 token；阴影收敛两档；时长改走 `--dur-*`；在 `test:contrast` 之外再加一条 lint（禁 `shadow-(sm|lg|2xl|inner)`、禁 `duration-` 非三档）。

### 3.9 同一语义在不同组件被手工稀释（比"违规"更隐蔽）

真正让界面显乱的不是单点违规，而是**同一个概念在不同组件长不一样**：

- **队名 5 档字号**：17px（`MatchCanvas.jsx:117`）/ 15px（`HeroCard.jsx:220,251`）/ 13px（`MatchRow.jsx:168,201`）/ 12px（`WeekView.jsx:593,599`）/ 11px（`WeekView.jsx:519`、`SameNightPicks.jsx:63`）
- **模态标题 3 档**：17px（`Onboarding.jsx:100`）/ 15px（`SettingsDrawer.jsx:191`）/ 13px（`StandingsModal.jsx:124`、`UpdateModal.jsx:133`）—— 而 `tailwind.config.js:31` 注释明写 `lg(17px)=模态标题`
- **两栏核心卡圆角 12 vs 16**：规范点名情报面板 = `xl(12px)`，实为 `rounded-2xl`（`IntelPanel.jsx:80,95`、`PlayerStage.jsx:949`）；而同一栏的舞台是 `rounded-xl`（`PlayerStage.jsx:805,856`）—— **右栏内部 12/16 混用**
- **Tab/分段控件 4 套实现**：`atoms.jsx:358-371` Segmented、`WeekView.jsx:279-298`、`IntelPanel.jsx:191-194`、`TopBar.jsx:137-141`（圆角/padding/字号/下划线各不相同）
- **图标 8 档尺寸**：`icons.jsx` 注释声称三档，实际调用出现 8/10/11/12/13/14/15/16/22；同语境混用（`WeekView.jsx:141` chevron 13 vs `:502` chevron 11）
- **焦点态 3 种写法**：`ring-2 accent/60`×38、`ring-1 accent/50`×9、`ring-1 accent/60`×7；另有 `SettingsDrawer.jsx`（12 个按钮 0 处）、`TeamPicker.jsx`、`UpdateModal.jsx`、`CommandPalette.jsx`、`Player.jsx` 完全依赖 `index.css:252` 的全局兜底
- **按下态缺失**：`active:` 全站仅 6 处，列表行（`MatchRow.jsx:91`、`WeekView.jsx:559`）无按下反馈

**建议**：与其继续加 token，不如**先做"同一语义只允许一个实现"** —— 队名 / 模态标题 / Tab / 图标 / 焦点态 / 按下态各定成一个原子组件或一个 mixin，然后逐处替换。这比再写一版规范有用。

## 四、信息设计层（本轮最值钱的部分）

### 4.1 「夜猫指数」缺刻度 —— 见 §一 主线二

具体建议（按实现成本从低到高）：

1. **最快**：在指数旁永远带上**比较基准**，如 `指数 2.5 · 本轮最高 27.2` 或 `2.5 / 今夜 5 场中第 3`。零算法改动。
2. **中等**：把长尾指数映射到稳定的 0–100 展示分（保留原始值在 tooltip），让"2.5"和"27.2"不再同框打架。
3. **最彻底**：**废掉星标与指数的并置**。要么星标只在详情页出现，要么把星标改成指数的可视化（同一信号的两种形态），不要让用户以为是两个东西。

另外，桌面行原用 `index >= 8`，移动端原用 `index >= 15` —— **同一个数字，两端对"值不值得点亮"的判断不同**（详见 §六）。本轮已抽 `INDEX_HIGHLIGHT_THRESHOLD = 8` 两端共用。

### 4.2 同一个数字一屏出现 5–6 次

以选中 AC米兰 vs 博洛尼亚为例（`.shots/review-1039/schedule-1440-dark.png`）：

1. 左栏行右侧 `指数 2.5`
2. 舞台中央胶囊 `指数 2.5 · S2 2.5h · ★☆☆`
3. 情报面板右上 `夜猫指数 2.5`
4. 「指数归因」末行 `综合指数 2.5`
5. 「睡眠代价」大字 `2.5h`
6. 「指数归因」`睡眠代价 2.5h（S2 中度）`

`IntelPanel.jsx:261-276` 已经在为**文案**做去重（注释写得很清楚），但**数字**没去重。

**建议**：定一条"一个数字一屏一次"的规则 —— 主舞台胶囊是唯一出处；面板头、归因末行、行右侧只在需要横向比较时出现（列表保留，单场面板去掉）。

### 4.3 指数归因画了五条进度条，三条是空的

「看点与代价」右栏的归因面板：看点星级 1 星（有条）、故事线加成 0.0（空条）、主队加成 0.0（空条）、联赛加成 0.0（空条）、睡眠代价 2.5h（有条）、观看占用 0.5h（小条）、综合指数 2.5。

**给 0.0 的项画一根空进度条，是纯噪声** —— 它既不传达大小，还挤占了空间。

**建议**：加成为 0 的项折叠成一行文字（`故事线 / 主队 / 联赛 无加成`），只给非零项画条；或改成 10-27 复核 P2-1 建议的**可验算结构**（`基础看点 10 + 故事线 0 + … = 10 → ÷ (1+2.5+0.5) → 2.5`）。

### 4.4 舞台上有两个"时间"在打架

舞台中央大字 `01:30` 是**开球时刻**，但它用的是倒计时级别的字号（`text-display` 44px + JetBrains Mono + 圆形光晕），下面又跟一行真正的倒计时 `距开球 10:45:36`。

我第一次看截图时就把 `01:30` 读成了倒计时。**一个长得像倒计时、字号比真倒计时还大的"开球时刻"，是误导。**

**建议**：
- 开球时刻降级为标题行的元信息（`10月29日 周四 01:30` 已经在右上角了，其实**是重复的**）；
- 舞台中央只留一个时间语义：赛前 = 倒计时（放大），进行中 = 比分（放大），终场 = 比分。

### 4.5 「7 熬夜负荷」柱状图等于没画

周计划左栏的七晚柱状图：3.5h / 3.5h / 4.5h / 4.5h / 3.5h。代码实际按 4.5h 归一化（不是 0–8h），3.5h 与 4.5h 的柱高约 30px vs 38px；但没有刻度与参考线，差异不足以支撑“看图决策”（见 `.shots/review-1039/week-1440-dark.png`）。没有 y 轴刻度、没有参考线，颜色又只是按档位上色 —— 这张图没有传达任何柱高之外的信息。

**建议**：这是"把熬夜画成时间"（§五）的最佳切入点 —— 与其画 7 根差不多高的柱子，不如画 **7 列夜猫日夜历**（22:00–06:00 纵轴），把每场画成时间块。它能同时解决：柱高无差异、同时开球不可见、睡眠成本抽象、以及"这周怎么看"没有画面。

> 这与 10-27 复核的 P2-5「把熬夜画成时间，而不是分数」**结论一致**，也与 `ui/stitch_modern_ui_design_system/week_budget_planner/` 设计稿底部那个七列夜历一致。三处独立得出同一结论，值得优先做。

### 4.6 日期条混用绝对日期与相对标签

赛程页日期条：`10/25 23场 | 前天 1场 | 昨天 3场 | 今天 5场 | 10/29 2场 | 10/30 3场`。

同一排里一半是绝对日期、一半是相对标签，扫读时无法建立连续感。且最右侧一枚被 mask 切断，看起来像渲染 bug（实际是 `.date-strip-mask` 的有意渐隐，但切到"半个数字"的观感不好）。

**建议**：统一成绝对日期 + 今天高亮（`10/26 | 10/27 | **10/28** | 10/29`），"前天/昨天/今天"作为 tooltip 或副标签。

### 4.7 积分榜：一处遮挡

`standings-1440-dark.png` 里，右下角浮层「共 20 队 · 滚动查看」**直接压在蒙扎那一行的"距前四 13 分"上**，没有渐隐遮罩托底。

积分榜本身做得很好（列头齐全、tabular 数字、"位置"列用"领先第 2 名 3 分 / 距前四 2 分"这种相对表述、"本场"标记、前四参考线），这处是唯一的硬伤。

**建议（已修）**：底部加渐隐 scrim，或给列表留 `padding-bottom`；本轮已补 40px 底部 spacer。

## 八、建议的方向性重构（不是修补）

前面都是"改哪里"。这里说"往哪去"。

### 8.1 把「熬夜」画成时间，而不是画成分数

现在睡眠成本是 `S2 · 2.5h` 这样的抽象徽章。对夜猫用户最直观的是一晚的时间轴：

```
22:00   23:00   00:00   01:00   02:00   03:00   04:00   05:00   06:00
   │                                                        │
   │  [23:00 赫尔城-伊普斯维奇 ────]                        │
   │              [00:30 利物浦-阿森纳 ────]                │
   │  ▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒ 睡眠窗口 ▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒ │
```

一张图同时回答：
- 今晚哪几场、什么时候（替代了分散的列表）
- **哪些同时开球**（重叠自然暴露 —— 10-27 的 P0-1 冲突问题在视觉上不言自明）
- 要熬到几点（成本不再是抽象数字）
- 周视图 = 7 条这样的轴，预算选择高亮

三处独立来源都指向这个方向：10-27 复核的 P2-5、原始设计稿 `week_budget_planner` 底部的七列夜历、以及本轮的柱状图失效分析。**这是与 FotMob / 懂球帝区分度最高的一步，也最符合"夜猫"品牌。**

### 8.2 重做「今晚」首屏为「决策卡」，而不是「转播台」

现在首屏的视觉重心是：舞台倒计时 + 线路 + 官方平台。这三样都是**开播之后**才用得上的。

真正该在 3 秒内读到的是一张**决策卡**：

```
┌──────────────────────────────────────────────┐
│ 今夜 5 场 · 1 场值得熬            夜猫指数 27.2 │
│                                              │
│  利物浦 vs 阿森纳   00:30   S2 2.5h   ★★★     │
│  └ 因为：主队出战 · 英超焦点 · 明晨无早场      │
│                                              │
│  其余 4 场（指数 2.5 / 2.5 / 2.0 / 2.0）       │
│  └ 全部低于 5.0 推荐线 → 今晚建议早睡          │
│                                              │
│  [ 查看这场 ]   [ 都不看，早点睡 ]            │
└──────────────────────────────────────────────┘
```

关键差异：
- **给结论，不给仪表盘**（"今晚建议早睡"是一句能行动的话）
- **把"不看"做成一等公民**（10-27 的 P1-5 已提，弱夜态至今没有被设计过 —— §二）
- 舞台与线路退到次级，开播后才接管

### 8.3 定一条「数字一屏一次」的排版纪律

现有的三条 token 纪律之外，加第四条：

> 4. **同一个数值在一屏之内只出现一次**，其余位置用引用或省略；横向比较用列表，纵向说明用面板。

这条能一次性清掉 §4.2、§4.3、§4.4 的重复与空条。
