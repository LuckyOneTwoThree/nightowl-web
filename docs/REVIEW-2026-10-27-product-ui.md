# 夜猫看台 · 产品与 UI 深度复核（2026-10-27）

> 范围：桌面端产品链路、桌面 UI/UX、手机端核心链路（代码级复核）。
> 方式：真实 Electron 窗口截图 + DOM 尺寸实测 + 关键纯函数实算 + 现有测试门禁；未修改产品代码。
> 截图：`.shots/review-1027/`（1440×900、1366×768、1120×700、1920×1080）。

---

## 一、结论先行

上一轮（v0.1.35）把「崩溃、防剧透、播放控制、快捷键、信息去重」这些**可信与可控**的底座补齐了，设计系统、对比度、渲染冒烟也都是干净的。

但这一轮深度复核暴露出的下一层问题，不在细节打磨，而在两个更底层的地方：

1. **周计划的时间模型不成立。** 算法把同一时刻开球的 4 场比赛都选进「本周精选」，并把 4 场睡眠成本相加；手机端「下一周」还把时间基准整体后移，导致未来周的计划被截断。周计划是产品三大承诺之一，这一项目前不能按字面使用。
2. **首屏的决策信号被稀释了。** 最该回答「今晚看哪场 / 值不值得熬」的位置，被 338px 的 Hero、297px 的倒计时舞台和 197px 的「接下来」占据；真正能比较今晚所有场次的列表在 1440 宽只有 145px 高，在 1366×768 只有 61px，在 1120×700 只剩 21px。

如果只做三件事，建议顺序是：

1. 先修 **P0 周计划时间模型**（同时开球冲突 + 手机未来周 + 周一凌晨归属），并补对应回归测试。
2. 再修 **P1 最小窗口与首屏层级**（1120 顶栏、左栏列表高度、Hero/接下来压缩、同夜推荐上移）。
3. 最后做 **P1 弱夜模式与数据文案**（「今晚无必看」给出真正结论、列表补指数、去重 2.5、W/D/L 可读）。

## 四、发现与建议

### P0-1 · 周计划把同时开球当成都能看，睡眠成本还相加

**证据**

- 10-31 23:00 四场全部进入 `plan.best`，`used` 为 4h。
- `src/core/engine.js` 的 `planWeek` 只约束预算与数量上限（`maxPicks`），没有任何时间冲突或比赛时长约束。
- 比赛时长常量 `MATCH_DURATION_MS = 120min` 已经存在，但计划器没有使用。
- 手机 `PlanScreen` 复用同一套 core，问题一致。

**影响**

- 「最多能看哪几场」这一核心承诺失效；预算也是错的（只看一场时成本应是 1h，而非 4h）。
- 用户按「本周精选」安排睡眠，结果四场同时开球；这是比任何视觉问题都更伤信任的逻辑缺陷。
- 「零成本顺带 12 场」也有同样问题：同一时段 12 场全部列出，用户实际只能看一场。

**建议**

1. 先做**最小正确版**：同一开球时刻最多选 1 场；把同组其余场次作为「同场次备选」展示，不计入预算。
2. 再做**完整版**：按 120 分钟区间做加权区间调度 / 每晚 Pareto 前沿，再与睡眠预算做背包；允许「23:00 看一场 + 01:30 看一场」这种不重叠组合。
3. UI 明确写「同时开球 · 只能看一场」，并把该组内最高指数场次标为推荐，不要用「4 场精选」。
4. 补测试：
   - `plan.best` 中任意两场的 `[kick, kick+120min)` 不重叠；
   - `used` 按同组最大成本或实际不重叠成本计算；
   - 手机下一周同样通过。

**注意**：这不仅是一个 UI 提示问题，修 UI 不修算法会出现「明明提示冲突，却仍算 4h」的自相矛盾。

### P0-2 · 手机「下一周」把时间基准整体后移，未来周计划被截断

**证据**

- `mobile/src/app/(tabs)/plan.tsx`：`computeWeek(now + weekOffset * 7 * DAY_MS, prefs)`。
- `computeWeek` 内部同时用这个 `nowTs` 做两件事：确定周窗口 + 判断「是否已开赛/已结束」（`isPickable`）。
- 于是查看下一周时，该周前半段（甚至周一整晚）被当作历史；`matches` 66 场、`days` 50 场、`best` 只剩周六 4 场。
- 用户看到「本周精选」很少，但下面日期条/日网格又有比赛；两者互相矛盾。

**建议**

- `computeWeek` 拆成两个参数：`weekAnchorTs`（看哪一周）与 `nowTs`（真实当前时间，用于 `isPickable` / 进行中判断）。
- 手机传 `weekAnchorTs = now + offset * 7d`，`nowTs = now`。
- 桌面当前周不受影响，但应复用同一语义，避免以后加「上一周/下一周」时再踩。
- 补测试：未来周的首日比赛只要还没开球，就必须出现在 `best` 候选池。

### P1-1 · 周网格与计划对「周一凌晨」的归属不一致

**证据**

- `computeWeek` 的 `matches` 按时间戳过滤（周一起点 → 下周一），`buildWeekDays` 却按 `owlDay`（凌晨 6 点前归前一天）归组。
- 结果：周一 00:00–06:00 的比赛在 `matches` 里，在 7 天网格里却找不到。
- 实测：周起始 11-02 时，周一凌晨 16 场全部落在网格外；`best` 里的 `LIV vs ARS` 也在网格外。
- 同一问题会出现在任何「周日深夜 → 周一凌晨」的焦点战；例如 11-02 00:30 的利物浦 vs 阿森纳。

**影响**

- 周度分布、周度建议、用户对「本周哪几天重」的判断都少了一整段；
- 用户从「本周精选」点进比赛后，在周网格里找不到它；
- 「周」既是日历周又是夜猫周，口径没有统一。

**建议**

- 明确产品定义：**周 = 7 个夜猫日（周一深夜 → 周日夜）**，还是**日历周（周一 00:00 → 周日 24:00）**。
- 对夜猫产品，建议选「7 个夜猫日」：`computeWeek` 用 `owlDay(m.t)` 判断归属；周一凌晨场自然归到「周日夜」，出现在周一前的周日格。
- 如果要保留日历周，则 `buildWeekDays` 必须按时间戳归组，并把周一凌晨标成「周一凌晨」而不是周日。
- 补不变量测试：`days` 中所有场次的并集 = `matches` 中所有未开赛/未结束场次（按当前周窗口）。

### P1-2 · 1120×700 / 1366×768：顶栏换行、今晚列表被挤到不可用

**证据（DOM 实测）**

- 1120×700：
  - `header` 固定 52px，但其子项高度为 48px/42px；nav 按钮高 48px，文字换行。
  - 品牌「夜猫看台」、三个视图标签、时钟「2026-10-27」、搜索「Ctrl K」、球队名、设置全部断行。
  - 左栏今晚列表 **21px**，滚动内容 490px；「未开赛 · 3」下面几乎看不到比赛行。
- 1366×768：
  - 顶栏正常，今晚列表 **61px**，滚动内容 478px；仍然只够露出 0–1 行。
- 共同原因：
  - Hero 338px + 「接下来」197px + section header 约 45px + 顶栏 52px + 上下 padding；
  - `NextUpRail` 是固定 dock，不参与压缩；
  - 今晚列表是 `flex-1`，被压到接近 0 时没有任何最小高度保护。

**影响**

- 1120 是应用声明的最小窗口，1366×768 是极常见的 Windows 笔记本分辨率；在这两档，**最主要的决策列表不可用**。
- 顶栏断行会让产品第一眼像「布局坏了」，比任何颜色问题都严重。
- 「接下来」是补白模块，却挤掉了主列表；主次颠倒。

**建议**

1. 顶栏：
   - 所有标签 `whitespace-nowrap`；
   - 宽度 <1280 时收起时钟 pill，保留 `LIVE`/更新时间即可；
   - 宽度 <1200 时搜索只留图标，`Ctrl K` 收进 title；
   - 视图标签在窄宽用短标签「今晚 / 本周 / 赛程」。
2. 左栏：
   - 给今晚列表 `min-h-[160px]`（或 3 行）保护；
   - `NextUpRail` 在高度 <800 时可折叠为「接下来 ▸」一行，或只显示 1 条；
   - 弱夜把 Hero 从 338px 压到约 220–240px（见 P1-3）；
   - 今晚列表移除 Hero 重复行（见 P1-4）。
3. 验收：
   - 在 1120×700 / 1366×768 下，首屏至少看到 3 场今晚比赛；
   - 顶栏所有按钮单行；
   - 把这两档加进 `check-render` 的断言，而不是只截图。

**这是本轮最值得先修的 UI 回归**：它不需要重做设计系统，只需重新分配高度和断点。

### P1-3 · 首屏层级倒置：舞台比情报短，决策模块在折叠线以下

**证据**

- 1440×900：舞台 720×297，情报面板 1047×415；情报比主舞台高 118px。
- 右栏 315×297 的「直播线路」卡只有 1 条线路和 6 个官方平台 chip，留下大块空白。
- 「同夜其他推荐」首屏只露出标题，真正能替代当前场次的选择在 y=789 之后。
- 1120×700：情报面板从 y=573 开始，首屏只能看到 127px；官方平台卡在情报之前。

**影响**

- 用户 3 秒内看到的是「倒计时 + 线路 + 官方平台」，而不是「为什么看这场 / 还有什么选择」；
- 比赛情报、指数归因、替代场次这些**决策信息**被工具信息压在下面；
- 主舞台和右栏都在「撑高度」，但撑出来的是空白，不是信息。

**建议**

- **弱夜/赛前 >2h**：舞台不要放巨幅倒计时，改为「今晚时间轴 + 本场结论 + 同夜备选」；倒计时缩成一行，仅在开球前 2h 放大。
- 把「官方平台 / 直播线路」压成舞台下方一条紧凑操作条，或收进按钮浮层；右栏让给「同夜其他推荐 / 双方后续」。
- 情报面板压缩：
  - 头部保留指数 + 睡眠档 + 2 条理由；
  - 「指数归因」折叠为「为什么是这个分数 ▸」；
  - 删除重复的 2.5 / 2.5h 第二次展示。
- 目标：1440×900 首屏同时看到**今晚列表 ≥3 行 + 同夜推荐 ≥2 行 + 情报头部**。

### P1-4 · 今晚列表缺少唯一的横向比较值，Hero 还在列表里重复一次

**证据**

- 桌面 `MatchRow` 的右侧在未开赛时显示「未开赛」；它既不显示夜猫指数，也不显示星级。
- `TonightView` 给每行算出了 `ev`，但只使用了 `ev.rivalry`，没有把 `index` 传给行组件。
- 手机 `MatchRow` 在未开赛时右侧显示 `index.toFixed(1)`，桌面没有。
- `TonightView` 渲染完整 `tonight.slice`，Hero 场次同时出现在 Hero 和列表第一行；手机 `TonightScreen` 明确 `filter(match.id !== hero.m.id)`。

**影响**

- 用户要比较今晚 3–15 场，只能看到时间、S2、雷区；没有统一的「谁更值得看」数值。
- Hero 重复行占用宝贵高度（在 1440 下正好是一行）；在 1120 下直接导致列表消失。
- 桌面「今晚 3 场」与列表里 Hero 重复，计数和列表语义不一致。

**建议**

- 未开赛行的右侧把「未开赛」换成 `index`（如 2.5），保留「未开赛」为 aria/tooltip；星级可放在指数旁。
- Hero 场次从列表中移除，或在行首标「今晚之选」并保留唯一一份；参考手机端。
- 列表头改成「其余 2 场」或「今晚 3 场 · 1 场推荐」，避免计数歧义。

### P1-5 · 弱夜 Hero 没有回答「为什么是这场」，也没有「不看了」的结论

**证据**

- 当前弱夜 Hero 的叙事输出来自 L3：
  ```
  headline: "S2 中度档 · 看点有限"
  lines: ["意甲 第 9 轮", "S2 中度档 · 睡眠成本 2.5h"]
  ```
- Hero 底部再次出现「S2 2.5h」；右侧情报面板再出现「2.5h / 2.5」；同一屏 3 次 2.5、3 次 2.5h。
- 舞台中央仍是 11:46:53 的巨幅倒计时；「今晚无必看」没有替代结论。
- 手机弱夜文案稍好：「今夜平淡 · 若熬夜看这一场」，但 CTA 仍是「查看详情」，没有「不看」选项。

**影响**

- 产品最核心的「帮你少熬几场」在弱夜没有落地：它仍然把一场低价值比赛包装成 Hero。
- 用户看不到「为什么不值得」「下一场更值得的是什么」「如果一定要看，选哪场」。
- 首屏信息重复，反而削弱了真正的决策信号。

**建议（弱夜模式）**

- 当 `heroTier === weak`：
  - Hero 改成紧凑「今晚结论」卡：`今晚 3 场，最高指数 2.5，未到值得熬的线（5.0）`；
  - 给出一个「如果一定要看」的备选，和一个「下一场更值得」的日期/对阵（可用现有 `nextFocal`/全量赛程算）；
  - 主行动是「查看下一场」或「看昨晚补看」，而不是「仍要观看」；
  - 舞台在距开球 >2h 时不放大倒计时，改为「今晚时间轴 / 3 场指数对比」。
- 强夜保留现有 Hero，但把叙事从「S2 中度档 · 看点有限」升级为一句真正的理由（故事线 / 德比 / 关注球队 / 欧战席位），L3 兜底至少写成「今晚三场里相对最高」并说明比较范围。

### P2-1 · 数据呈现的可读性：W/D/L、赛季列、交锋范围、归因

**证据**

- 舞台「近 5 场」使用 5 个彩色圆点（绿/灰/红），只有 hover title；没有 W/D/L 文本，色觉障碍用户无法读取。
- 数据视角同一组数据使用「胜 / 平 / 负」方块，两处表达不一致。
- 舞台「赛季 2-2-3 / 6-1-0」没有列头，只有 `title="胜-平-负"`；新用户很容易读成积分或得失球。
- 舞台写「历史交锋 暂无交锋」，数据视角写「两队本赛季尚未直接交锋」；数据实际只含单赛季，前者的「历史」容易误导。
- 「指数归因」行混用了星级、加成、成本、观看占用；`1/3 + 0 + 0` 与 `2.5` 不构成可验算的关系，用户只能相信，不能理解。
- 舞台 ticker 在赛前固定写「赛前情报与线路已就绪」；如果本地服务不可用或线路为 0，右侧会显示「待开播/无可用」，两处矛盾。

**建议**

- 舞台的 W/D/L 直接复用数据视角的带字方块（`胜/平/负`），不要只用颜色。
- 赛季列显式加列头：`胜-平-负`；数字旁给「场」或「轮」。
- 「暂无交锋」统一为「本赛季暂无交锋」或「当前数据集内暂无交锋」。
- 归因面板改成可验算的结构：
  - `基础看点 10 + 故事线 0 + 主队 0 + 联赛 0 = 10`
  - `÷ (1 + 2.5 + 0.5) = 2.5`
  - 或者只显示「3 个理由 + 一个成本结论」，把公式收进 Hint。
- ticker 根据 `lines.length / scrapeError / service health` 生成文案，不要写死「已就绪」。

### P2-2 · 「今晚」与「次日凌晨」的口径没有在界面上解释

**证据**

- 左栏标题「今晚赛程 · 10月27日 周二」，第一场卡片写「10月28日 周三 01:30」；
- 赛程页「今天 3 场」实际是 10-28 凌晨 3 场；
- Hero 写「10月28日 周三 01:30」，同一屏顶部写「今晚观赛」；
- README 有「夜猫日」概念，但界面没有一句话解释。

**建议**

- 列表时间改成 `今夜 01:30` / `明晨 01:30`，或在分区标题旁加 `含次日凌晨`；
- 日期条「今天」加 tooltip「夜猫日：06:00 前归前一夜」；
- 赛程页选中日期的标题写「10-27 夜（含 10-28 凌晨）」，避免「今天」与「10/28」并置。

### P2-3 · 桌面与手机的关键信息/交互不一致

| 项目 | 桌面 | 手机 |
| :--- | :--- | :--- |
| 今晚 Hero 是否重复在列表 | 重复 | 已过滤 |
| 未开赛行是否显示指数 | 不显示 | 显示 |
| 弱夜文案 | 「今夜无必看 / 仍要观看」 | 「今夜平淡 · 若熬夜看这一场 / 查看详情」 |
| 单场提醒 | 无 | 有「设置提醒」 |
| 周导航 | 只能本周 | 可上一周/下一周 |
| 最小字号 | 11px（有规范） | `fontSize.xxs = 10` |
| 球队页 | 无 | 有 |

**建议**

- 先对齐前三项（成本低、收益直接）：过滤 Hero 重复、桌面行加指数、弱夜文案统一。
- 周导航在桌面可以不做，但手机未来周先用 P0-2 修正确。
- 单场提醒建议在批次 2（托盘/通知）完成后补桌面版，否则「关注球队/今晚之选」之外的场次无法提醒。
- 手机 10px 建议只用于真正的角标，正文元信息回到 11px。

### P2-4 · 右栏「官方平台」占了决策位

**证据**

- 1440 下右栏 315×297，只有一条线路和 6 个官方平台 chip；空白约 1/3。
- 同夜推荐在首屏以下；1120 下整个情报面板在首屏以下。
- 官方平台在赛后还会同时出现在「官方集锦」「官方全场回放」两处。

**建议**

- 官方平台是「执行入口」，不是「决策信息」：压成舞台下方一行（或「更多平台」浮层）。
- 右栏优先放「同夜其他推荐 / 双方后续」；这两块才是「换一场 / 放弃这场」的决策依据。
- 赛后把「回顾 / 集锦 / 回放」收进一个「赛后」折叠区，避免三组重复入口。

### P2-5 · 产品机会：把「熬夜」画成时间，而不是分数

当前睡眠成本是 `S2 / 2.5h` 这样的抽象徽章。对夜猫用户，最直观的是**一晚的时间轴**：

```
22:00  23:00  00:00  01:00  02:00  03:00  04:00  05:00
      [本场 23:00-01:00]
                    [同夜 01:30-03:30]
[睡眠窗口 ................]
```

- 今晚视图：用一条 22:00–06:00 的时间轴，把所有场次画成块；推荐场次高亮，重叠场次自然暴露。
- 本周视图：7 条夜间时间轴（周一夜 → 周日夜），预算选择高亮；这比「4 个精选行」更像一个「观赛计划」。
- 它会同时解决：
  - 同时开球冲突不可见；
  - 睡眠成本抽象；
  - 「接下来」与「同夜」的空间竞争；
  - 周计划在折叠线以下的问题。
- 这是与竞品（FotMob/懂球帝）区分度最高的一步，也最符合「夜猫」品牌。

**附加机会：昨晚战报**

- 当前补看只给最近 4 天前 3 场；如果用户睡过了整个夜晚，缺少一个「昨晚 6 场结果 + 哪 3 场值得补看 + 你关注的队」的晨间摘要。
- 建议在「今晚」顶部（或 07:00–12:00 时段）提供一个可折叠的「昨晚战报」，遵守防剧透；这比再加一个数据面板更符合「少熬、补看」的产品定位。

## 五、建议的实施顺序（轻量版）

### 第一批：只修「时间模型」（P0）

1. `planWeek` 增加不重叠约束（先做同一开球时刻，再做 120 分钟区间）。
2. `computeWeek` 拆分 `weekAnchorTs` 与 `nowTs`；手机未来周用真实 now 判断可看性。
3. 周窗口与 `buildWeekDays` 统一到 `owlDay`（7 个夜猫日）。
4. 补 3 条测试：同开球不重复、未来周首日可见、`days` 并集 = `matches`。
5. UI 加「同时开球 · 只能看一场」的组内提示，并修正预算 `used`。

### 第二批：最小窗口与首屏层级（P1）

1. 顶栏 1120/1366 断点：不换行、收时钟/搜索文案。
2. 今晚列表 `min-height`，`NextUpRail` 可折叠/低高度隐藏。
3. Hero 移除重复行；桌面行补指数。
4. 弱夜 Hero 压缩为「今晚结论」卡。
5. 同夜推荐上移/右栏化，官方平台下沉。

### 第三批：数据文案与跨端（P2）

1. W/D/L、赛季列头、交锋范围、归因可验算。
2. 「今夜/明晨」口径。
3. 桌面/手机前三项对齐；手机 10px 回 11px。
4. 单场提醒（依赖批次 2 的托盘/通知）。
5. 时间轴 / 昨晚战报作为下一轮产品实验，不要和本轮修复混做。

### 建议延后

- 桌面球队页（手机已有；先看真实使用频率）。
- 桌面多周导航（先把手机未来周修正确）。
- 更复杂的双开/多屏模式（当前单播放器，先不做）。

## 六、总体评价

**做得好的地方**

- 设计系统与 token 纪律是真的：语义色、字号下限、对比度、焦点态、阴影层级、reduced-motion 都有明确约束，并且测试通过。
- 数据诚实是产品资产：防剧透、积分榜截止、上游未提供、待录比分、补看窗口，都没有用假数据糊弄。
- 观赛执行链路完整：线路、代理、断流、快捷键、静音起播、回顾、集锦，这些不是「demo 级」。
- 空态/异常态/边界态的意识很强，比大多数个人项目成熟。

**最需要警惕的地方**

- 产品正在从「决策工具」滑向「广播数据台」：舞台、线路、官方平台、积分榜都很完整，但「今晚看哪场」的结论和「这周怎么看」的时间模型不够硬。
- 上轮优化解决了很多「别骗人」的问题；这一轮要解决「别算错」和「别把结论埋起来」的问题。
- 1120/1366 的布局说明：设计稿的 1440 观感不能替代最小窗口的可用性。以后每个 UI 批次都应把 1120×700 作为硬门禁，而不只是截图留档。
