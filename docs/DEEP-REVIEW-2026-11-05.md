## 一、第三份审查抓到我漏的（4 条，全部复核成立）

### 1. 首屏静态引入播放器子树

`src/App.jsx` 顶层：

```js
import StandingsModal from './components/StandingsModal.jsx';   // :28
import PlayerStage from './components/PlayerStage.jsx';         // :29
import SettingsDrawer from './components/SettingsDrawer.jsx';   // :31
import UpdateModal from './components/UpdateModal.jsx';         // :34
import ScheduleChanges from './components/ScheduleChanges.jsx'; // :38
```

只有 `Player.jsx`（artplayer + hls.js，705KB）是 `lazy()` 的。**PlayerStage 连同 4 个面板组件（HighlightsPanel / LiveMatchPanel / MatchCanvas / RecapTimeline）共 2,296 行，全部在首屏 chunk 里**——只看今晚推荐也要先加载播放器外壳。

**但收益被高估了**：

| 事实 | 数字 |
| :-- | :-- |
| 首屏 `index-*.js` | 778 KB（gzip 201 KB） |
| 播放器子树行数 / 全 src | 2,296 / 17,371 ≈ **13%** |
| 懒加载后预计节省 | 约 80–150 KB（gzip 25–45 KB） |
| Electron 加载方式 | 本地磁盘，无网络往返 |

「降到 300 KB 以内」不现实：React 19 运行时本身约 130 KB，业务代码约 640 KB。在 Electron 本地加载下，这 13% 的收益**用户感知不到**。

**定性**：为未来 Web 分发做的准备，不是当前缺陷。优先级 P3。

### 2. 桌面端没有静态检查门禁

`mobile` 有 `tsc --noEmit`；桌面端 `src/` + `server/` 既无 TypeScript 也无 ESLint/Biome。`PlayerStage.jsx` 1,549 行、`App.jsx` 1,240 行全靠运行时测试兜底。

**这条成立，且比我 11-04 记的「手机端零行为测试」更靠前**——桌面至少还有 1,130 条断言，手机是既无静态检查也无行为测试。

### 3. 手机播放器没有防盗链容灾

`mobile/src/app/player.tsx` 只有两处 `headers: { 'User-Agent': USER_AGENT }`（:119 / :159），没有 m3u8 改写、没有 Referer 注入、没有分片代理。桌面的 `server/proxy.js` 能做全量 URI 重写 + 分片流控，手机完全没有。

**但要修正定性**：这不是「实现缺失」，是**平台限制**。RN 环境跑不了本地 HTTP 服务，`expo-video` 也不支持自定义 loader（只能吃 URL，不能吃字符串）。要做只能「fetch → 改写 → 写临时文件 → 喂 file:// URL」，这条路径在 iOS/Android 都很脆弱。

**定性**：已知取舍，写进 README 比改代码更实际。

### 4. PlayerStage 单文件多职责

1,549 行 / 16 个 `useState` / 8+ 职责（线路池、断流自愈、快捷键、通知过滤、实时 ticker、剧场布局、深链、回顾轴）。我 11-04 只记了 App.jsx 1,240 行，漏了这个更大的。

## 三、需要修正的（5 条）

### 1. Electron 版本号混淆

它写「当前 `electron` 版本为 **33.2.0**」。实际：`package.json` 声明 `^33.2.0`，**安装的是 33.4.11**。声明与实际不是一回事。

### 2. 升级目标版本是错的

它建议「升至当前长期支持（LTS）版本（如 **Electron 34/35+**）」。

Electron 没有 LTS，只有「最新 3 个 stable major」的支持窗口。实测 `releases.electronjs.org`：

```
近期 stable major: 45, 44, 43
33.x 已发布版本数: 76
```

**34 和 35 一样早已 EOL**。升到 34 只是从一个过期的版本换到另一个过期的版本。正确目标是 43/44/45。

### 3. 「saveFixtures 阻塞事件循环」被夸大

它说「大体积 JSON 序列化与文件写入会短时间阻塞 Node 主事件循环」。

实测（1,897 场 / 215 KB）：

```
序列化 0.3 ms | 写入 3.7 ms | rename 4.6 ms
总计阻塞 8.6 ms
```

8.6 ms 不到一帧（16.7 ms），在每 200 ms 一次请求的串行同步里完全被吸收。**不值得改**。

而且它建议的「异步写」会引入新问题：`runSyncStage` 是多阶段的（ESPN → openfootball），异步写会产生并发写竞争，反而需要加锁。现在的 `writeFileSync + renameSync` 同步原子写是**正确的选择**。

### 4. 「缺 E2E」判断不准确

它说 `check:render` 是「通过 headless Electron 测量 DOM 属性与布局」。

实际 `check-render.mjs` 是真实 Electron + 真实 dist + 真实交互，已覆盖：命令面板开/关与焦点归还、点击比赛进入详情、积分榜 20 行、补看队列写入 localStorage、防剧透揭晓、失效深链不白屏、切视图保留滚动位置、`inert` 焦点隔离、键盘导航。共 82 项。

这是**框架选型差异**（自有脚本 vs Playwright），不是覆盖度缺失。而且这是个 Electron 单窗口应用，没有跨浏览器需求 —— 引入 Playwright 的边际收益主要是「换一套 API」，不是「多测了东西」。

真正缺的是：**手机端零行为测试**（G3），以及「设置抽屉改预算」这类组合链路。

### 5. 优先级排序把大重构放太高

它把「数据管道下沉为共享纯 JS 模块」列为 **P1**。

这是**大重构**：8 对文件涉及 Node `http/fs` 与 RN `fetch/AsyncStorage` 两套环境，下沉需要注入适配层。风险是把「一处改动、两端核对」变成「一处改动、两端 + 一个抽象层核对」。收益是长期维护成本，但当前 `verify-pipeline` 已经能**看见**差异（虽然不能保证等价）。

当前更紧急的是数据口径问题（见第四章）。**这条应该 P2**，且必须先补手机行为测试才能做——否则重构成什么样都不知道对不对。

## 四、三份审查的共同盲区：没有人测「升级路径」

第三份审查通读了代码、跑了测试、查了 Git 历史，但**没有模拟「老用户从 v0.1.49 升到 v0.1.50 后看到什么」**。

而这正是当前最紧急的问题。我昨天发版后实测：

| 指标 | 升级前 | 升级后 |
| :-- | :-- | :-- |
| 可见场次 | ~526 | 1,897 |
| 赛程页日期组 | ~30 | 136（2,033 行） |
| `pendingCount` | 个位数 | **114** |
| `stalePendingCount` | 个位数 | **105** |

根因：内置快照 `src/data/fixtures.json` 是 8 月中旬出厂时抓的赛程，1,897 场里**只有 392 场有比分（20.7%）**。旧行为下用户文件完全遮蔽它，问题看不见；v0.1.50 改成按 id 合并后全部暴露。

分布：114 场过期未录里，**104 场在 14 天同步窗口内**（首次同步会补掉），**10 场在 14–30 天**——`activeSyncTargets` 窗口是 14 天，这 10 场永远不会被查，会**永久显示「上游缺分」**。
