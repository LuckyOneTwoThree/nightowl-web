> **定位**：开工前的算法验证环境。用真实数据确认「移植无损」并摸清算法的真实行为。
> **状态**：✅ 已完成（2026-09-12）
> **对应任务**：任务计划 SP-0（已完成）· T2-3 算法移植（本目录产出验证通过后可作为起点）

## 为什么先做这个

主方案与审查意见对算法风险的两处判断，**经实测被证伪或不够准确**。与其在写代码时踩坑，不如先用真实数据问清楚。

本目录回答三个问题：

1. **移植是否无损？** —— 原版 `engine.js`（CommonJS，读烘焙字段 `s`）与移植版（ESM，运行时计算档位）在全量 1,897 场上是否一致
2. **三条铁律在真实数据上是否成立？** —— 关注联赛 +8 的边界、tbd 排除、完赛状态兼容
3. **算法的真实输出长什么样？** —— 未来 90 夜 Hero、各预算档的背包结果、指数分布、看点覆盖

## 核心结论

### 一、移植无损（可放心改造）

| 比对项 | 不一致处数 |
| :--- | ---: |
| 原版 `tierOf`（读烘焙 `s`） vs 移植版 `tierOf`（运行时） | **0 / 1897** |
| 原版 `owlIndex` vs 移植版 `owlIndex` | **0 / 1897** |
| 原版 `evaluate().star` vs 移植版 | **0 / 1897** |

→ `tierOf` 改为运行时计算是**安全等价改造**，**可直接废弃数据中的烘焙字段 `s`**。

### 二、三条铁律全部成立

- 铁律一：已选 5 个联赛 → `leagueBonus` = 8；已选 6 个 → 0 ✅
- 铁律二：`pickToday` / `planWeek` / `minefield` 输出中 tbd 泄漏 **0** ✅
- 铁律三：`isFinished()` 同时认 `done` 与 `ft` ✅

### 三、三个需要产品决策的发现

| # | 发现 | 级别 | 决策 |
| :--- | :--- | :--- | :--- |
| A | **主队加成不影响 Hero 排序**（加成取 0~40，90 夜结果差异均为 0/90）。原方案 §3.6 的定性有误——真正的问题是 `W ÷ (1 + 成本)` 让"零成本"获得乘性特权，导致指数失去区分度（凌晨主队欧冠 8.2 < 傍晚 ★1 中立赛 10.0） | 🟡 中 | **D6** |
| B | **背包退化**：S0 场次重量为 0 → 不消耗容量 → 全部装入。**周预算 1.0h 也返回 20 场推荐**，与设计稿「入选 3 场」矛盾 | 🔴 阻塞 | **D8** |
| C | **Hero 周末/平日断层**：周末 Hero 平均指数 21.8（★3 占 34.5%），平日仅 6.3（16.7%）。设计稿只呈现了周末形态 | 🟠 高 | **D9** |
