## 一、产品定位与核心原则

### 1.1 核心定位

专为熬夜球迷打造的 **本地纯净观赛工作台（Owl Match Station）**。

### 1.2 使用边界（硬约束）

| 约束 | 内容 |
| :--- | :--- |
| 服务监听 | **仅 `127.0.0.1`**，绝不监听 `0.0.0.0`，不对外暴露 |
| 部署 | **不部署公网、不做成可一键托管的分发形态** |
| 使用范围 | 仅本人本机观看，不向他人提供、不承担任何对外再分发 |
| 数据 | 全部本地存储，零云依赖、零登录、零鉴权 |

### 1.3 三大第一原则

1. **桌面体验第一**：针对宽屏场景深度打磨，不为移动端牺牲信息密度与操作效率；
2. **看球链路第一**：点击任何一场比赛，都能稳定、高清、无广告地拉起直播流；
3. **极简无负担**：不引入过重的中间件，不引入复杂跨端转码。

### 1.4 交付形态结论：桌面应用而非浏览器标签页

个人使用场景下，**唯一需要本地服务进程的方案，用桌面外壳托管它**。两种形态的能力差异：

| 能力 | 纯浏览器标签页 | Electron 单进程 |
| :--- | :--- | :--- |
| 启动方式 | 需手动起服务 + 开浏览器 | **一次点击**，服务随窗口起停 |
| 第三方页面兜底 | `X-Frame-Options` 直接白屏；沙箱内**无法**移除广告 | **内嵌 webview + 广告域名拦截 + 选择器隐藏**，纯净可用 |
| 开赛提醒 | 无 | **系统通知**（赛前 15 分钟） |
| 全局快捷键 | 无 | **有**（唤起 / 静音 / 全屏） |
| 画中画与多屏 | 受浏览器策略限制 | 完整控制 |

**结论**：产品名里的「纯净」在纯浏览器形态下**无法兑现**（跨域 iframe 拿不到 DOM，去不了广告）。采用 Electron 托管后，前端代码零改动复用，**Shell 层是本方案唯一差异点**，因此下方 Steps 1–3 不受形态影响。

## 三、核心算法大脑

算法继承自原项目 `miniprogram/utils/engine.js`，改写为纯前端 ES Module `src/core/engine.js`。

### 3.1 调用契约（必须遵守）

算法函数对**输入集合**有严格要求，传错集合会得出错误结论：

| 函数 | 输入集合 | 取数方式 |
| :--- | :--- | :--- |
| `pickToday` | **今晚的场次** | 按 `owlDay(m.t) === nightOf(now)` 过滤。**绝不可传全量赛程**，否则会选出数月后的比赛 |
| `planWeek` | **本周的场次** | `weekStartBJ()` 得周一 00:00（北京）→ +7 天 |
| `minefield` | 本周窗口 | 同上 |
| `nextFocal` | 全量未来场次 | 全量 + 时间戳比较 |
| `replays` | 全量已赛场次 | `isFinished()` 过滤 |

### 3.2 核心判据三铁律

1. **关注联赛加成**：`leagueBonus` 仅在已选关注联赛 < 6 时给予 +8 分；全选 6 个时不加分；
2. **时间待定（`tbd`）排除**：`tbd === true` 的场次不可信，不担任今晚之选、不进预算背包、不进雷区，**也不显示睡眠档位徽章**；
3. **完赛状态兼容**：`isFinished(m)` 同时兼容 `'done'`（ESPN 抓取源）与 `'ft'`（历史手工数据）。

### 3.3 睡眠成本模型（北京时间 · 运行时计算）

**关键设计**：档位一律**运行时**由开球时间计算，**不依赖数据中的预计算字段**。这样数据同步后档位自动跟随，不存在「时间更新了、档位还是旧的」的错配。

```javascript
export const SLEEP_TIERS = [
  { tier: 0, label: 'S0', cost: 0.0, zh: '零成本', desc: '白天至 22:30' },
  { tier: 1, label: 'S1', cost: 1.0, zh: '轻度',   desc: '22:30–00:30 开球' },
  { tier: 2, label: 'S2', cost: 2.5, zh: '中度',   desc: '00:30–02:30 黄金修仙档' },
  { tier: 3, label: 'S3', cost: 3.5, zh: '重度',   desc: '02:30–04:00 深夜死线档' },
  { tier: 4, label: 'S4', cost: 4.5, zh: '极限',   desc: '04:00–07:00 黎明折磨档' }
];

// 唯一入口：所有档位判定都从这里出，不允许读数据里的静态档位字段
export function sleepTier(timeStr) {
  const [hh, mm] = timeStr.split('T')[1].split(':').map(Number);
  const minutes = hh * 60 + mm;
  if (minutes <= 30) return SLEEP_TIERS[1];            // 00:00-00:30
  if (minutes <= 150) return SLEEP_TIERS[2];           // 00:30-02:30
  if (minutes < 240) return SLEEP_TIERS[3];            // 02:30-04:00
  if (minutes < 420) return SLEEP_TIERS[4];            // 04:00-07:00
  if (minutes <= 22 * 60 + 30) return SLEEP_TIERS[0];  // 白天-22:30
  return SLEEP_TIERS[1];                               // 22:30-24:00
}

export function tierOf(match) { return sleepTier(match.t); }
```

### 3.4 时区口径（不可简化）

数据时间形如 `2026-08-16T01:30`，是**北京时间墙钟、无时区后缀**。全部换算走纯 UTC 算术，**禁止用 `new Date(t)` 做本地解析**——否则在非 +8 时区的设备上「今晚之选」会整体错位。

| 函数 | 职责 |
| :--- | :--- |
| `ts(t)` | 北京墙钟串 → 真实时间戳（`Date.UTC(...) - 8h`） |
| `owlDay(t)` | 夜猫口径「展示日」：**00:00–06:00 的场次归属前一晚** |
| `nightOf(now)` | 夜猫口径「今晚」，设备时区无关 |
| `weekStartBJ(now)` | 当前北京所在周的周一日期串 + 周一 00:00（北京）真实时间戳 |
| `matchState(m, now)` | 推导 `sched / live / ended_pending / finished / pp` |

**状态机**：`sched` → （赛前 30 分钟）`soon`（预热态，UI 派生）→ `live`（开球至 +120 分钟）→ `ended_pending`（等比分）→ `finished`。
其中 `soon` 为前端派生态，不由数据落库。

### 3.5 算法能力清单（7 项）

| 能力 | 函数 | 说明 |
| :--- | :--- | :--- |
| 今晚之选 | `pickToday` | 当日主队出战绝对优先 → 关注联赛高星焦点战 → 低睡眠成本 → 故事线节点 |
| 睡眠成本分档 | `sleepTier` / `tierOf` | S0–S4 |
| 夜猫指数 | `owlIndex` | `W ÷ (1 + 睡眠成本)` |
| 本周背包 | `planWeek` + `knapsack` | 主队优先 + 关注联赛背包 + 跨联赛焦点战填补 |
| 雷区预警 | `minefield` | S3+ 且 ★ 且无故事线 → 建议睡觉 |
| 无球日降级 | `nextFocal` + `countdown` | 无球日展示下一场焦点战倒计时 |
| 补番推荐 | `replays` | 已赛高分场次（延后启用） |

### 3.6 两处权重需标定（不建议照搬默认值）

1. **夜猫指数中主队加成（+25 ≈ 2.5 星）几乎压垮睡眠成本差异**：04:00 的主队战（W=55，÷5.5）= 指数 10.0，与 20:30 的 ★1 中立赛（W=10，÷1.0）= 10.0 打平。即「凌晨 4 点爬起来看主队」与「晚饭后随手看场球」被判等价。是否合适需明确定标；
2. **背包「主队预算内必保」缺少容忍度**：周预算 4.0h 遇主队 S3（3.5h）会吃掉 87.5% 预算，剩余 0.5h 装不下任何场次。建议加**单场成本上限**或**主队软保底**（超阈值降级为「建议观看」而非强制入包）。

### 4.1 数据保鲜（MVP 核心，与看球链路同等优先级）

赛程不是静态数据：全赛季 1,897 场中，**1,023 场（53.9%）的开球时间由电视台提前 2–4 周公布**，且每日产生新的完赛比分。因此本地服务必须包含数据保鲜模块。

| 保鲜项 | 现状 | 同步动作 |
| :--- | :--- | :--- |
| **比分** `sc` | 快照仅 159 场已赛 | 拉取最新赛果，写入比分 |
| **真实开球时间** | 1,023 场为占位值（`04:00` / `02:00`） | 官方公布后回填真实时间，并解除 `tbd` |
| **改期** `pp` | 无 | 标注延期并在日历原位提示 |

**硬约束**：

1. **`st` 取值域限定为 `sched` / `done` / `pp`**。进行中的状态**一律不落库**，由 `matchState()` 从时间推导。原因：`pickToday` / `planWeek` / `minefield` 均硬过滤 `st === 'sched'`，若把进行中的场次写成其他值，Hero 卡片会在开球那一刻消失；
2. **档位与时间强绑定**：解除 `tbd` 后，睡眠档位由 `tierOf()` 自动重算（见 §3.3），不存在残留旧档位的可能；
3. 刷新时机：应用启动时 + 定时（15 分钟）+ 手动刷新按钮；失败静默降级为本地快照，不阻塞界面。

### 4.2 流代理与 M3U8 重写（必须做完整）

各大直播流 CDN 均校验 `Referer`。代理的核心是一个通用转发接口，**M3U8 重写必须覆盖全部 URI 载体**，缺一项就会出现「能起播但一拖进度条就崩」：

| 需重写的载体 | 用途 | 漏改后果 |
| :--- | :--- | :--- |
| 普通分片行（`.ts`） | 视频分片 | 直接 404 |
| `#EXT-X-STREAM-INF` 下一行的**变体 URI** | master playlist 指向各清晰度子清单 | **切清晰度即失败**（最常见坑，入口通常是主清单） |
| `#EXT-X-KEY:URI` | 加密密钥地址 | 解密失败，黑屏 |
| `#EXT-X-MAP:URI` | fMP4 初始化段 | 起播黑屏 / 解码失败 |
| `#EXT-X-MEDIA:URI` | 独立音轨 / 字幕轨 | **「英文原声」线路直接作废** |
| `#EXT-X-I-FRAME-STREAM-INF:URI` | 拖动预览缩略图 | 预览失效 |
| `#EXT-X-PART:URI` | 低延迟 HLS 分片 | 低延迟源全废 |

**统一规则**：逐行扫描，凡 URI 型属性与文本行，**先基于入口 URL 解析为绝对地址**（分片多为相对路径），再统一改写为代理路径。FLV 为单流地址，无需重写，走纯转发。

### 4.3 代理层硬约束

| 项 | 要求 |
| :--- | :--- |
| 监听地址 | **仅 `127.0.0.1`** |
| 目标白名单 | 仅允许已配置的直播域名（`rules.json` 维护），拒绝任意 URL |
| 请求头 | 仅允许放行 `Referer` / `User-Agent` 等白名单字段，不透传任意头 |
| 请求能力 | 透传 `Content-Type`，**支持 `Range` 请求**（拖动与分片必需） |
| 缓存策略 | `m3u8` 索引**不缓存**（否则永远播旧切片）；`.ts` 分片可长缓存 |
| 流量控制 | 并发上限 + 单请求超时；赛前批量预热时必须限速，避免上游封 IP |
| 流式转发 | 逐块 pipe，不做内存驻留（单场 1080p 数据量在 GB 级） |
| 查询串 | **完整透传**上游 `query` / `token`（签名 URL 会过期，不可丢弃参数） |

### 4.4 队名对齐（Matcher）与置信度分级

* 基于球队字典与中文别名表（`曼城=曼彻斯特城`、`国米=国际米兰`、`拜仁=拜仁慕尼黑` 等）；
* 抓取标题按 `vs / v / 对` 切分，双队匹配为主、开球时间为辅；
* **时间比较一律用绝对时间戳**，不可比较日期字符串（凌晨场次归前一晚，直接比字符串会差一天）；
* 三档置信度，避免误播（凌晨点开却是别的队，体验伤害极大）：

| 置信度 | 判据 | 行为 |
| :--- | :--- | :--- |
| 高 | 双队精确名 + 时间差 ≤ 30 分钟 | 直接绑定，点亮【🔴 正在直播】 |
| 中 | 别名模糊匹配 / 时间差 30 分钟–2 小时 | 标注「可能匹配，请确认」后再播放 |
| 低 | 单队匹配或时间差 > 2 小时 | 不进线路池，仅提供【↗ 直达原站】 |

* 保留**用户纠正回路**（「这不是这场比赛」→ 写入本地黑名单），让匹配质量可持续改进。

### 4.5 双层降级（绝不白屏）

1. **主选（Tier 1）**：解析成功的 `.m3u8` / `.flv` 直链，通过 ArtPlayer 内置播放；
2. **兜底（Tier 2）**：提不到直链时，**桌面外壳内嵌第三方页面 + 广告域名拦截 + 元素选择器隐藏**；同时始终提供【↗ 直达原站观看】按钮（自动带上对阵搜索词）。

> 说明：Tier 2 的去广告能力依赖桌面外壳（见 §1.4）。此前规划的「浏览器沙箱 iframe 去广告」在纯 Web 形态下不成立——跨域 iframe 无法访问内部 DOM，且多数站点会以 `X-Frame-Options` / CSP 拒绝被嵌套。

### 4.6 开赛预热

赛前 30 分钟卡片显示【即将开赛】，并预取线路；预取结果设**有效期（TTL）**——直播源地址常带限时签名，超时后点击需重新解析。注意第三方房间常在开赛前 5–15 分钟才上线，预取失败要静默重试并保留占位态。

## 五、系统架构与技术栈

### 5.1 工程结构

```
nightowl-web/
├── electron/                    # 桌面外壳（主进程）
│   ├── main.js                  # 窗口管理、服务随窗口起停、系统通知、全局快捷键
│   ├── preload.js               # 内嵌页面注入（广告位隐藏）
│   └── adblock.json             # 广告域名与选择器规则（外置可改）
├── server/                      # 本地服务（约 4–5 个核心文件）
│   ├── index.js                 # 服务入口、静态资源托管、接口路由
│   ├── scores.js                # 数据保鲜：比分 / 开球时间 / 改期
│   ├── scraper.js               # 第三方站点抓取与队名对齐
│   ├── proxy.js                 # M3U8 重写与流媒体代理
│   └── rules.json               # 站点提取规则、请求头、域名白名单（外置可改）
└── src/                         # 前端应用（React 18 + Vite + Tailwind）
    ├── core/engine.js           # 算法大脑
    ├── data/                    # 数据层（见 5.2）
    ├── components/              # HeroCard / ScheduleList / WatchPanel / Player
    └── App.jsx                  # 桌面双栏布局
```

### 5.2 数据层（6 项，缺一不可）

| 文件 | 内容 | 在算法中的作用 |
| :--- | :--- | :--- |
| `fixtures.json` | 全量赛程（含比分、状态、`tbd`） | 赛程层 |
| `teams.json` | 球队字典（含队色、标签） | 队名映射与视觉 |
| `rivalries.json` | 焦点对阵 | 德比 → 基准 ★★★ |
| `storylines.json` | 故事线（含节点与关键节点） | 关键节点升星 + 指数加成 |
| `recommendations.json` | 人工推荐层（星级、看点、冷知识） | 星级覆盖与看点文案 |
| `crests/` | 队徽图片资源 | 赛程卡片渲染 |

> 数据以「人工只维护推荐层与故事线层，其余由脚本生成」为原则。

### 5.3 技术选型

| 层 | 选型 | 说明 |
| :--- | :--- | :--- |
| 桌面外壳 | Electron | 单进程托管服务，解锁纯净内嵌、通知、快捷键 |
| 前端 | React 18 + Vite + Tailwind CSS | 开发心智低，构建快 |
| 播放器 | ArtPlayer + hls.js（+ mpegts.js） | 桌面端 HLS 为主路径；FLV 走 MSE，仅作 Chromium 内核增强，不作为跨浏览器承诺 |
| 本地服务 | Node.js 原生 HTTP（或 Hono / Express） | 直接复用当前环境 Node，无额外运行库 |
| 网页解析 | cheerio | 快速提取房间列表 |
| 长列表 | 虚拟滚动 | 全量赛程列表必须虚拟化，否则赛季中后期滚动会拖垮 |

### 5.4 建设纪律

* 依赖一律装在本项目 `node_modules`，不使用全局安装；
* 数据更新走脚本，不手工改数据文件；别名表与提取规则需可校验、可快速替换；
* 抓取失败与「今天没有比赛」必须在界面上区分，不可混淆。

### 6.2 字段数据可达性（线框设计的前提）

界面上每个展示项都必须有明确来源，**不允许设计没有数据源的字段**：

| 展示项 | 来源 |
| :--- | :--- |
| 时间 / 队徽 / 队名 / 比分 / 状态 | 数据层（`fixtures` + `teams` + `crests`） |
| 睡眠档位 S0–S4、夜猫指数 | 算法运行时计算 |
| 星级、德比名、故事线提示 | 算法计算 + 数据层 |
| 看点条目、冷知识 | 看点供给三层（见 6.3） |
| 多路线路标签 | 抓取结果实时 |
| 提示「差 2 小时」类时间信息 | 需要额外数据源，**本期不做** |

### 6.3 看点内容的三层供给

人工推荐层目前只覆盖全赛季的 1.6%，因此看点必须是**分层降级**而非「有则显示、无则空白」：

| 层 | 来源 | 覆盖 |
| :--- | :--- | :--- |
| L1 人工精修 | 推荐层 `points` / `trivia` | 焦点战。**只精修「今晚之选」一张卡片**，每周 1–2 条，成本可控 |
| L2 规则合成 | 德比名 / 故事线描述 / 球队标签 / 睡眠档位提示 | 覆盖德比、六强内战、故事线节点 |
| L3 通用兜底 | 「凌晨 S2 档 · 看点有限」类档位与状态提示 | **其余全部场次**，保证永不空白 |

## 七、敏捷开发里程碑

以**「最快速度跑通第一场比赛观看」**为唯一目标，严控执行次序：

```
Step 1 骨架与算法 ──▶ Step 2 服务与流代理 ──▶ Step 3 数据保鲜与抓取 ──▶ Step 4 外壳与体验打磨
```

| 步骤 | 目标 | 前置 | 验收指标 |
| :--- | :--- | :--- | :--- |
| **Step 1** 骨架与算法 | 建立 Vite + React 工程，移植算法与 6 项数据层 | — | ① 双栏渲染正常；② 今晚之选、0-1 背包、雷区预警输出与旧版一致；③ 全量赛程列表筛选与滚动流畅（已虚拟化） |
| **Step 2** 服务与流代理 | 建立本地服务，实现 `/api/proxy` 与 M3U8 全量重写 | **可行性采样**：手工抓 20 场比赛房间，统计「可提取可播裸直链」的成功率，并区分 DRM 与非 DRM | ① 手动输入一个带防盗链的 m3u8，播放器流畅播放、无 403；② 拖动进度条与切换清晰度均不报错；③ 直链成功率有真实数字，据此决定播放器是主路径还是增强路径 |
| **Step 3** 数据保鲜与抓取 | 接入赛果与赛程同步；实现第三方站点抓取与队名对齐 | **源站考察**：确认目标站点的 HTML 可静态解析（无 JS 挑战），并准备 ≥2 个源站规则互为备份 | ① 赛程显示真实开球时间，最新比分正确落库；② 点击赛程卡片【🔴 立即观赛】右侧大屏自动换源出画面；③ 单一源站失效不影响其他线路 |
| **Step 4** 外壳与体验打磨 | 桌面外壳、多线路切换、内嵌兜底、快捷键与通知 | — | ① 一次点击启动，服务随窗口起停；② 焦点战多线路秒切；③ 提不到流时内嵌兜底可用且无广告弹窗；④ 赛前 15 分钟系统通知可达 |

## 总结

本方案剔除了非核心的跨端包袱与边缘功能，**直击痛点：算法决策 + 极清看球**；同时补齐了让数据「活起来」的保鲜链路与让界面「不空白」的看点分层，明确了本地个人使用的边界。开发时严格依据 Step 1 ~ Step 4 的节奏与验收指标实施。
