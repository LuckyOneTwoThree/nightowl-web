## 二、修正：我此前单路审查稿中的 2 处错误

### 错 1（重要）：把方案 §3.2 的 `getSleepTier` 当成了算法运行路径

**我此前的判断**：把方案 §3.2 贴出的 `getSleepTier(timeStr)` 与 `engine.js` 的 `sleepTier(t)` 逐行对照，结论"✅ 已有"，然后把问题归结为"漏了 `owlDay` 等日历函数"。

**实际情况**：`sleepTier()` **只在构建期被调用一次**，运行期从不调用它：

```javascript
// tools/build_fixtures.js:253  ——  唯一的调用点
s: engine.sleepTier(t).tier, sc, tv: null,
```

运行期走的是另一条路：

```javascript
// miniprogram/utils/engine.js:70
function tierOf(match) { return TIERS[match.s] || TIERS[0]; }
//                                            ↑ 注意这个兜底
```

**所以方案 §3.2 贴出来的那个函数根本不是算法运行期用的路径。** 真正的运行期依赖是数据里每条记录携带的烘焙字段 `s`：

| `s` 档 | S0 | S1 | S2 | S3 | S4 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 场次 | 213 | 271 | 505 | 195 | 713 |

**后果（静默崩坏，不报错）**：若新数据管线丢失 `s` 字段，`|| TIERS[0]` 兜底会让**所有**场次的睡眠成本被判为 0 → 夜猫指数分母恒为 1、背包重量恒为 0 → 算法全线失真且无任何异常抛出。

**补充验证（本轮新增）**：我复算了 1,897 场，**烘焙 `s` 与运行时 `sleepTier(t)` 有 0 处不一致**。所以同行提出的"把 `tierOf` 改为从 `m.t` 运行时计算"是**安全等价改造**，可放心执行——这是本次修订中性价比最高的一刀。

> 另修正一处措辞：我此前写"方案的 `getSleepTier` 丢掉了 tbd 前置过滤"不够准确——原 `sleepTier` 本身也不做 tbd 过滤，过滤动作在调用方（`pickToday` / `planWeek` / `minefield` 的 `!m.tbd`）。真正的风险是"占位时间被当真实时间烘焙进 `s`"，见 §4.3。

### 错 2：旧审查问题复用率算错

**我此前的判断**："18 项中约 11 项落在已删模块内"——与我自己表里列出的条目数不符。

**修正后的准确口径**：

| 分类 | 数量 | 明细 |
| :--- | :--- | :--- |
| 完全消除（模块已删） | **13 项** | P0-1、P0-2、P1-3、P1-4、P1-6、P1-7、P1-8、P1-9、P1-10、P2-14、P2-15、P2-16、P2-18 |
| 转化为等价问题 | **5 项** | P1-5（tbd）、P2-11（排序）、P2-12（闩锁→抓取降级）、P2-13（别名表）、P2-17（定时器与视图重建） |

结论方向不变（**减法正确**），但数字须用修正后的 13 / 5。

### 3.1 实测：Node 原生 fetch 的流没有 `.pipe()`

```
Node v22.22.2 → body 类型: ReadableStream | typeof .pipe: undefined | typeof .pipeTo: function
调用 .pipe() → TypeError: b.pipe is not a function
Node v26.8.2  → typeof .pipe: undefined | typeof .pipeTo: function
```

方案 §4.1 写的 `upstreamResponse.body.pipe(res)` **在 Node 22 与 Node 26 上均当场抛错**。正确写法为 `Readable.fromWeb(res.body).pipe(out)`。这是 Step 2 会第一时间踩到的坑，必须写进方案。

### 3.4 补强：旧版偏好键与迁移路径

我此前只指出 `getApp()` 兜底会让 `leagueBonus` 恒为 0，但更前置的问题是**方案 UI 里根本没有"关注联赛"的选择入口**。旧版实现（`app.js:48-80`）：

```javascript
getFollowed()        → wx.getStorageSync('followedTeams')    || []
getFollowedLeagues() → wx.getStorageSync('followedLeagues')  // 含"5 联赛自动补 UCL"的兼容 shim
```

**迁移路径很干净**：Web 版用同名 localStorage 键即可，顺手把那段 shim 删掉。但要补两件事：① 顶栏或设置面板加"关注联赛"多选入口；② **注意易混淆点**——方案 §6.1 左栏的筛选药丸 `[全部][英超][欧冠][只看主队]` 是**列表过滤**，与**关注联赛偏好**语义不同，开发极易混为一谈（前者不影响算法，后者是铁律一的输入）。

## 四、三路审查的共同盲区：本轮新增 4 项发现

### 4.1 内容供给缺口：人工推荐层实际覆盖率仅 **1.6%**，93.3% 的场次没有任何看点信号

三路审查都只提到"31 条 vs 计划 250-300 条"，**没有人算过覆盖率，也没人把它连到 UI 后果**。我算了：

| 指标 | 实测值 |
| :--- | :--- |
| 有人工推荐条目的场次 | **31 / 1,897 = 1.6%** |
| 其中带 `points`（看点列表）的 | 31 场 |
| 其中带 `trivia`（冷知识）的 | **仅 15 场** |
| 覆盖的轮次范围 | 各联赛**第 1–2 轮**（揭幕周）+ 德国超级杯 + 欧冠第 1 轮 |

再加自动兜底信号后的覆盖分布：

| 看点信号来源 | 场次 |
| :--- | :--- |
| 人工推荐层 `rec` | 31 |
| 故事线节点 `story` | 36 |
| 德比对阵 `rivalry` | 39 |
| BIG SIX 内战 `big6` | 22 |
| **完全无信号 `none`** | **1,769（93.3%）** |

**对照原 PM 定稿的规划**：文档明确写"推荐层（约 250–300 条／季，人工维护）"，并强调"人工只维护推荐层与故事线层——这是 1,752 场规模下唯一可持续的方式"。**但实际只落地了揭幕周种子。**

**与方案 UI 的冲突**：方案 §6.1 右栏线框明确画着「比赛核心看点：• 榜首大战，双方近 5 次交锋各胜 2 场平 1 场」——**对 93.3% 的场次，这块面板没有任何内容可渲染**。

**这是产品决策，不是工程 bug。** 三条路，方案里必须显式选一条：

| 选项 | 含义 | 成本 |
| :--- | :--- | :--- |
| A. 接受降级 | 只有焦点战有富文本看点，其余场次显示德比名 / 故事线描述 / 档位提示 | 0 |
| B. 补齐人工层 | 按原规划做到 250–300 条/季 ≈ **每周 8–10 条** | 持续人力 |
| C. 自动生成看点 | 从可用信号（队标 `tag`、故事线 `desc`、档位、历史比分）合成一句话 | 一次性开发 |

**我的建议**：以 A 为 MVP 基线 + C 做一期增强（数据层已有 `teams.tag`、`storylines.desc`、`rec.trivia` 三类可用文本），B 只对"今晚之选"这一张 Hero 卡片做人工精修（每周 1–2 条，成本可控）。**但绝不能让开发以为"看点数据是齐的"。**

### 4.2 线框图里至少有 2 处字段在整个数据层不存在

我逐字段核了方案 §6.1 线框图的承诺：

| 线框承诺 | 数据层实况 | 判定 |
| :--- | :--- | :--- |
| 「双方近 5 次交锋各胜 2 场平 1 场」 | 全仓库**无 H2H / 历史交锋数据**（实测无命中） | 🔴 **字段不存在** |
| 「睡眠成本评级: S3（建议次日补觉 1.5 小时）」 | 算法只输出 `cost` 数值，**无"补觉时长"字段** | 🔴 **字段不存在**（需算法新增或改为文案模板） |
| 「状态: 🔴 LIVE 进行中」 | `matchState()` 可从时间推导 ✅ | 🟢 可达 |
| 「线路1: 咪咕原画 1080p 50fps」 | `tv` 字段**全为 null（0 条非空）**，无频道/码率元数据 | 🟠 清晰度标签只能来自抓取源原始文案，不能作结构化字段 |
| 「👄 咪咕原画 1080p 50fps」播放器角标 | 同上 | 🟠 同上 |

**建议**：把 §6.1 的线框图整改为**「数据可达性标注版」**——每个展示字段标注来源四选一：`算法输出` / `静态数据` / `抓取实时` / `不存在`。这一步成本极低，但能一次性消除"线框是愿望图"的隐患。

### 4.3 最关键的耦合：tbd 占位时间 × 烘焙档位 —— 54% 的睡眠档位是假值

三路审查都指出了 tbd 占比过半，但**没人发现 tbd 与烘焙字段 `s` 之间的强耦合**。我实测：

| tbd 场次的占位时间 | 场次 | 由此烘焙出的 `s` 档 |
| :--- | :--- | :--- |
| `04:00` | 586 | **S4**（成本 4.5h） |
| `02:00` | 437 | **S2**（成本 2.5h） |
| **合计** | **1,023** | 只有 S2 / S4 两个值 |

也就是说：**1,023 场（53.9%）的睡眠成本档位是由占位时间算出来的假值，而且这个假值被烘焙进数据、算法运行期直接读取。**

**这带来一个此前无人指出的严重失败模式**：

> 如果只补回"真实开球时间同步"，却不同时重算 `s`：
> - tbd 被解除 → 这些场次**首次进入** `pickToday` / `planWeek` / `minefield` 的候选池（此前被 `!m.tbd` 挡在门外）
> - 但它们携带的是**过期的假档位**（一律 S2 / S4，而真实时间多数落在 S1–S3）
> - 结果：赛季 54% 的场次的"今晚之选"与背包规划**建立在错误权重上**，而且不会报错

**这给了"把 `tierOf` 改为运行时从 `m.t` 计算"第二个、也是更硬的理由**——不改的话，数据同步等于只改了一半。**这条必须写进方案，与"数据保鲜模块"同批实施。**

### 4.4 `st` 取值域与 `pickToday` 硬过滤存在冲突风险

三个核心算法函数都硬编码了 `m.st === 'sched'` 作为入选前提：

```javascript
.filter(function (m) { return m.st === 'sched' && !m.tbd; })   // pickToday / planWeek / minefield
```

若补回 ESPN 同步后，把进行中的场次写入 `st = 'live'`（ESPN state 为 `in`）：

> **正在进行的焦点战会被排除出"今晚之选"，Hero 卡片会在开球那一刻消失。**

**建议在方案里显式约束同步写回的 `st` 取值域**：只写 `sched` / `done` / `pp`；`live` 一律由 `matchState()` 从时间推导，**不落库**。这条约束不写，两个模块上线后会互相打架。

## 八、最终建议

**方案的"观赛链路"部分扎实，问题集中在一个字上：数据。**

四项必补（对应清单 1、2、3、5）+ 一项必决（消费场景）落地后，方案的闭环就完整了：

1. **数据要能活**——补回数据保鲜模块（比分 / 真实开球时间 / 改期）；
2. **数据要够用**——6 项数据层清单 + 111 个队徽，别漏；
3. **数据要准**——废弃烘焙字段 `s`，档位运行时算，否则同步只改一半；
4. **数据要能落地到 UI**——看点覆盖率只有 1.6%，线框图里还有 2 个字段根本不存在，先决策再排期；
5. **先钉死消费场景**——本地单机 / 局域网 / 公网，决定纯 Web 还是 Electron 单进程。

补齐这五项，就可以按 Step 1–4 的节奏直接开工。
