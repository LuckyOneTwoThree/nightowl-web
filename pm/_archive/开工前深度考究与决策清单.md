## 〇、结论先行

**1. 需要出产品支撑文档，但顺序不是「先写 PRD」，而是「先对账 → 再定决策 → 后写 PRD」。**

原因是本次项目的实际推进顺序是**设计先行**（Stitch 稿已产出 5 套页面），而方案文档是**技术先行**（主方案 §5 架构占了大头）。两者之间缺一层**需求规格**做咬合。此时直接写 PRD，会把设计稿里已经跑偏的东西原样固化进去，冲突无处安放。

**2. 可复用资产比预期更完整，真正的缺口集中在一处：需求规格层与数据供给层的咬合。**

算法（`engine.js` 499 行）可 100% 移植；数据层 6 项齐全；UI 视觉体系（token / 字体 / 睡眠徽章）已成型且质量高。**缺口不在"从零造"，在"把已造的东西对齐"。**

**3. 考究发现 9 类实质问题，其中 4 类必须在开工前处置。**

| 级别 | 问题 | 不处置的后果 |
| :--- | :--- | :--- |

## 二、七项深度考究发现

### 发现 1｜设计规范立了法，Stitch 执行时破了法，且无人对账

`ui/UI设计规范与视觉设计系统.md` §五 明确写了三条禁令：不得出现"近5次交锋统计"（H2H）、"球员对抗指数"、"补觉具体分钟数"。

**但实测 Stitch 产出的 4 套 `code.html` 中，出现了 8 类同样性质的无源字段：**

| 设计稿字段原文 | 出现位置 | 数据层实况 | 判定 |
| :--- | :--- | :--- | :--- |
| `xG: 1.84 vs 1.22` / `xG预期: 1.76` / `xG 预期进球率` | tonight、week、schedule | **全库无 xG 数据** | 🔴 不存在 |
| `控球: 48% - 52%` / `控球推进` / `控球压制倾向` | tonight、schedule | 无控球率统计 | 🔴 不存在 |
| `68% 成功率` / `89% 传球精度` / `94% / 91%` | tonight、schedule | 无技术统计 | 🔴 不存在 |
| `4-3-3 高位逼抢` / `4-3-3 战术压迫` | tonight、week | 无阵型/首发数据 | 🔴 不存在 |
| `节律扰动: 78%` / `节律诊断` / `节律认知负荷模拟` | tonight、week | 无生物节律模型 | 🔴 不存在 |
| `对抗强度: 极高 (Tier 1)` / `42%` | tonight | 同上 | 🔴 不存在 |
| `2 Mbps` / `1080p 50fps` / `6.2 Mbps` | tonight、schedule | **`tv` 字段非空 0 条** | 🔴 不存在 |
| `咖啡因窗口现已完全关闭` / `补觉窗口` / `补觉即可维持正常昼夜节律` | tonight、week、schedule | 算法只输出 `cost` 数值，无医学字段 | 🟠 需降级为通识文案 |

> **为什么这条是阻塞级**：开发 Agent 拿到的输入若同时包含「设计稿（有这些字段）」和「数据层（没这些字段）」，最省事的路径是**写死假数据**让界面"看起来还原"。这一旦发生，产品定位里的"算法算得准"就塌了——界面在说谎。**必须在开发前用书面结论钉死每个字段的去留。**

**处置建议**：以《数据可达性对账表》为唯一判据，对设计稿做一次**字段级整改**（保留可达 / 换可达替代 / 删除）。

### 发现 2｜`teams.tag` 语义错位 —— 规范本身写错了字段含义

`ui/UI设计规范与视觉设计系统.md` §五 写：

> ✅ 球队风格标签（来自 `teams.json` 的 `tag` 字段，如"攻势足球"）

**实测结果与规范描述不符：**

| 核实项 | 实测值 |
| :--- | :--- |
| `teams` 总数 | 111 |
| 有 `tag` 字段的球队 | **仅 17 支（15.3%）** |
| `tag` 去重值 | **只有 2 个：「卫冕冠军」「升班马」** |
| 样例 | 阿森纳=卫冕冠军、考文垂=升班马、伊普斯维奇=升班马、弗罗西诺内=升班马… |
| 无 `tag` 球队 | **94 支** |

**结论**：`teams.tag` 是**赛季身份标签**（谁是卫冕冠军、谁是升班马），**不是战术风格标签**。"攻势足球 / 传控压迫"这类值**在数据层根本不存在**，规范里的举例是自己臆想的。

而设计稿右栏「战术风格矩阵」卡片（阿森纳【传控压迫·青年近卫军】vs 曼城【传控统治·进攻狂潮】）正是建立在这个错误假设上。

**处置建议（三选一，需拍板）**：

| 选项 | 做法 | 成本 | 我的评估 |
| :--- | :--- | :--- | :--- |
| **A（推荐）** | 把右栏第三列从"战术风格"改为**「赛季身份」**：显示卫冕冠军/升班马标签，无标签时显示联赛 + 联赛排名位（另一套可见信号） | 低 | 尊重真实数据，且"卫冕冠军首战""升班马保级"本身就有点击欲 |
| B | 扩充 `teams.json`，为 111 队人工补齐战术风格标签 | 中（一次性人工） | 数据是主观定性，维护成本高，且与"算法可复算"的调性冲突 |
| C | 删除右栏第三列，改为两列布局 | 低 | 干净但损失一列信息密度 |

### 发现 3｜信息架构出现"重复导航"，需二选一

**规范原文**（UI 规范 §一）：左栏 38% 顶部设 `[🌙 今晚] [📊 本周] [📅 赛程]` 三个 Tab；无其他导航。

**Stitch 实产结构**（实读 `tonight_match_station/code.html`）：

| 元素 | 规范要求 | 实产情况 | 冲突 |
| :--- | :--- | :--- | :--- |
| 38% / 62% 栅格 | 左栏 38%（min 420px / max 540px），右栏 62% | ✅ 保留（`w-[38%] min-w-[420px] max-w-[500px]`） | 🟡 `max-w` 为 500px，规范写 540px，提示词写 520px —— **三处不一致** |
| 三个 Tab | 只在左栏顶部 | ⚠️ **左栏有，顶栏也有一组**（同组 Tab 出现 2 处） | 🔴 重复导航 |
| 左侧竖排图标栏 | **规范中不存在** | ⚠️ 新增 `w-14 min-w-[56px]` 图标 rail，含 5 个图标（有重复 `data-path` 指向同一视图） | 🔴 净新增元素 |
| 顶栏高度 / 交通灯避让 | 52px + `pl-20` | ✅ 一致 | — |

**影响**：开发看到两份"权威"，必然自行取舍；且左侧 rail 会挤压本已紧张的 1440px 宽度下的左栏空间。

**处置建议（二选一，需拍板）**：
- **A（推荐）**：**承认 Stitch 的新结构**，但做减法 —— 保留顶栏 Tab，**删除左栏重复 Tab 与左侧 rail**，把 56px 还给内容区；同步修订 UI 规范。
  - 理由：顶栏 Tab 位置更符合桌面工作台习惯，且释放了左栏纵向空间（正是状态机指南 §五 想解决的问题）。
- **B**：回归规范 —— 删除顶栏 Tab 与左侧 rail，Tab 回到左栏顶部。

### 发现 4｜Stitch 只产出了"理想态"，8 类状态没有设计

Stitch 每套页面给的是一张**最好看的那一帧**。但本产品的真实状态空间远不止此：

| # | 缺失状态 | 触发条件 | 数据/算法依据 | 缺了会怎样 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | **无球日 / 全部 tbd** | 当晚无 `sched && !tbd` 场次 | `pickToday` 返回 `hero: null` | Hero 卡空白，直接崩 |
| 2 | **赛前态（即将开赛）** | 开球前 30 分钟内 | `matchState() → 'sched'` + 时间差 | 右栏无内容，设计稿只画了 LIVE |
| 3 | **已完赛态 / ended_pending** | `st='done'` 或已过 120 分钟待录比分 | `matchState() → 'finished' / 'ended_pending'` | 右栏"战报"设计稿承诺了但无源（见对账表） |
| 4 | **防剧透揭晓态** | 已赛场次点击揭晓 | 状态机指南 §四 有描述，无视觉稿 | 交互有规则、视觉无样式 |
| 5 | **数据同步中 / 同步失败** | 保鲜模块请求中或失败 | 主方案 §4.1「失败静默降级」 | 用户不知道看到的是不是最新数据 |
| 6 | **抓取失败 ≠ 今天没有比赛** | 两个必须区分 | 技术清单明确要求 | 文案混淆，误导用户 |
| 7 | **线路全部失败 → 降级内嵌** | Tier 1 全灭 | 主方案 §4.5 双层降级 | 无降级视觉，白屏 |
| 8 | **预算紧凑态（手风琴折叠）** | 默认态 | 状态机指南 §五 有规则，无视觉稿 | 有规则无样式 |
| 9 | **搜索/筛选无结果** | 列表空 | — | 空白页 |

> 这 9 类状态是 PRD 要补的**第一项硬内容**。状态覆盖不全，是前端返工的最大来源。

### 发现 5｜"直播中"的数据链路未定义

设计稿大量出现：`🔴 LIVE 65'`、`2 - 1`、顶栏「● 3 场比赛正在进行中」、`65:14` 时间轴。

**拆开看这两个数字的来源：**

| 展示项 | 是否可达 | 依据 |
| :--- | :--- | :--- |
| **进行分钟**（`65'`） | ✅ **可推导** | `matchState()` 从开球时间 + 当前时间算，无需外部数据 |
| **实时比分**（`2-1`） | ❌ **不可达** | 数据层 `st` 只有 `sched`/`done`，无 `live`；且方案硬约束"**live 一律不落库**"。15 分钟粒度的保鲜同步**不构成实时比分** |
| 顶栏「3 场进行中」 | ✅ 可推导 | 由 `matchState()` 全量推导计数 |
| 播放器时间轴 `65:14` | ✅ 可推导 | 同进行分钟 |

**结论**：设计稿的"LIVE + 实时比分"当前只有一半能兑现。**必须拍板**：

| 选项 | 做法 | 代价 | 我的评估 |
| :--- | :--- | :--- | :--- |
| **A（推荐）** | 进行分钟照常显示；比分位显示**开球前比分（空）或"—"**，并在完赛后由保鲜模块落库 | 0 | 诚实。深夜看球时"比赛进行到 65 分钟"已是强信号 |
| B | 新增实时比分轮询（1–2 分钟粒度，独立于 15 分钟保鲜） | 中（多一条数据链路 + 限速考量） | 体验最好，但引入新的外部依赖与封 IP 风险 |
| C | 由 ESPN 保鲜同步顺带取 live 比分（15 分钟粒度） | 低 | "65 分钟显示的是 20 分钟前的比分"，比不显示更糟 |

### 发现 6｜算法风险被定性错了：真正的问题不是"主队加成"，是"零成本双重特权"

> **本节已于 2026-09-12 用真实数据跑验证后重写。** 原判断（引自主方案 §3.6 与审查意见）经实测**定性有误**，更正如下。
> 验证环境：`spike/algo-baseline/`（ESM 移植版引擎 + 原版交叉比对，全量 1,897 场）

**先看已被证伪的那条**：

主方案 §3.6 称"主队加成 +25 几乎压垮睡眠成本差异"，担心它会让 Hero 选错。实测（90 夜窗口，加成取 0 / 5 / 10 / 15 / 25 / 40）：

| 主队加成 | Hero 结果与原版的差异数 |
| ---: | ---: |
| +0 | 0 / 90 |
| +5 | 0 / 90 |
| +10 | 0 / 90 |
| +15 | 0 / 90 |
| +40 | 0 / 90 |

**原因**：`pickToday` 排序的**第 1 优先级是 `isFollowed` 布尔硬比较**，权重只改变指数数值，根本不参与排序。**"主队加成会不会让 Hero 选错"这个问题本身不成立。**

**真正的问题在这里**。夜猫指数公式是 `W ÷ (1 + 睡眠成本)`，这让"成本 0"获得了一个**乘性特权**（分母恒为 1）。实测后果：

| 场次 | 时间 | 档位 | 星级 | 夜猫指数 |
| :--- | :--- | :--- | ---: | ---: |
| SLA vs ARS（欧冠客场） | 04:00 | **S4** | ★★ | **8.2** |
| ARS vs BVB（欧冠） | 04:00 | **S4** | ★★★ | 10.9 |
| SUN vs ARS | 03:00 | S3 | ★★★ | 13.3 |
| — 对照 — 任意 S0 ★1 中立赛 | 20:00 前后 | S0 | ★ | **10.0（155 场恒定）** |

**即：凌晨 4 点爬起来看主队踢欧冠（指数 8.2），在指数上不如傍晚随便一场 ★1 中立赛（10.0）。** 这直接违背"指数高 = 更值得熬"的直觉映射。

并且这个特权是**双重**的——它同时作用于背包：重量 = `成本 × 2`，S0 场次**重量为 0**，在 0-1 背包中不消耗容量（详见发现 8）。

**根因（产品层，不是工程层）**：模型只算了**睡眠成本**，没算**观看成本**。一场 20:00 的比赛确实不影响睡眠，但仍要占用 2 小时——**睡眠成本 ≠ 观看成本**。当前模型把"晚上随便看多少场都行"当成了前提。

### 发现 8｜🔴 0-1 背包在真实数据上**退化**（新增，两份既有文档均未发现）

**这是本次验证跑出来的最严重问题，比"主队硬保"严重得多。**

**现象**：本周窗口实测（`weekStartBJ` 起 7 天，66 场赛程）：

| 周预算 | 背包入选场次 | 实际占用 | 其中 S0 场次 | 最大单场占预算 |
| ---: | ---: | ---: | ---: | ---: |
| **1.0h** | **20** | 1.0h | 19 | 100% |
| 2.5h | **21** | 2.0h | 19 | 40% |
| 4.0h | **20** | 3.5h | 19 | 88% |
| 6.0h | **22** | 5.5h | 19 | 58% |
| 8.0h | **24** | 7.5h | 19 | 44% |

**用户设 1 小时预算，算法给出 20 场推荐。**

**机制**：背包重量 = `睡眠成本 × 2`。S0 场次成本为 0 → **重量为 0** → 在 0-1 背包中**不消耗容量**，有多少装多少；而每个 S0 场次价值 = 指数 10.0 × 10 = 100 分。于是算法把**当周全部 19 场零成本场次一次装入**。

**与设计稿的冲突**：Stitch 设计稿写的是「算法精选组合（**已自动入选 3 场**）」。真实算法给出的是一张 20 场清单——**这不是"规划"，是"全选"**。

**三个修复方案实测对比**（周预算 4.0h）：

| 方案 | 入选场次 | 占用 | 评价 |
| :--- | ---: | ---: | :--- |
| 原版（现状） | 20 | 3.5h | ❌ 退化 |
| ① 数量上限 N=5 | 5 | 3.5h | ✅ 但 S0 仍挤占名额 |
| ② S0 分离为「零成本顺带」单列 | 1 | 3.5h | ✅ 预算内只剩真正要熬的场次 |
| **③ 数量上限 N=5 + S0 分离** | **1** | **3.5h** | ✅ **推荐**：预算内 1 场（主队 S3），另列 19 场零成本顺带 |

> **产品判断**：方案③把"预算内必选"与"零成本顺带"拆成两个语义区，才符合用户设 4 小时额度的真实意图——**额度是用来约束熬夜的，不是用来约束"顺便看一眼"的**。这也正好对上设计稿「已自动入选 3 场」的表达。

### 发现 9｜Hero 质量存在「周末 / 平日」断层（新增）

**现象**：全赛季 131 个夜猫日中，有赛 85 晚、无赛 46 晚。按周末/平日拆分 Hero 质量：

| 分组 | 夜数 | Hero 平均指数 | ★1 | ★2 | ★3 | ★3 占比 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 周末（周五–周日） | 55 | **21.8** | 17 | 19 | 19 | **34.5%** |
| 平日（周一–周四） | 30 | **6.3** | 13 | 12 | 5 | 16.7% |

平日 Hero 样例：

| 夜猫日 | Hero | 星级 | 指数 |
| :--- | :--- | ---: | ---: |
| 2026-09-15 | RAY vs ESP | ★ | 2.9 |
| 2026-09-17 | BET vs GET | ★ | 2.9 |
| 2026-10-19 | MZA vs CAG | ★ | 5.0 |
| 2026-09-10 | FCB vs BOD | ★★ | 5.6 |

**问题**：Stitch 设计稿的 Hero 卡表现的是「★★★ · 夜猫指数 28.5 · 争冠天王山对决」——**那只是周末形态**。平日大量夜晚的 Hero 是"矮子里拔将军"（★1、指数 2.9–5.0），用同一张高光卡片去呈现会显得用力过猛且不可信。

**处置建议**：为 Hero 卡定义**质量分档**，低分档走降级形态（如：弱化"唯一焦点"措辞、改为"今晚可看"、或直接切到"下一场焦点战倒计时"）。具体分档阈值需拍板（见决策 D9）。

## 六、任务安排总纲

### 6.1 主轴

> **先钉死"能显示什么"，再谈"怎么显示得好看"；先把算法跑对，再把画面接上。**

原因：本产品的护城河是**算法可信度**（"今晚之选"要让人服气）。画面再漂亮，若 Hero 推荐不符合直觉、或界面数据是假的，产品就失去了存在理由。

### 6.2 四个阶段

| 阶段 | 名称 | 目标 | 关键产出 | 是否可并行 |
| :--- | :--- | :--- | :--- | :--- |
| **P0** | 对账定源 | 消灭愿望字段、唯一化信息架构、定死 4 项决策 | D1 对账表 + 5 项裁决 + 设计稿整改清单 | 与 P1 并行 |

| **P2** | 骨架跑通 | Vite+React 工程起、算法移植、6 项数据层迁移、双栏渲染 | 可跑的本地前端（数据真实、无直播） | **P2 与 P3 的 Spike 可并行** |
| **P3** | 链路打通 | 本地服务 + 流代理 + 数据保鲜 + 抓取对齐 | 第一场比赛真实观看跑通 | — |

| 可并行 | 内容 | 理由 |

1. **不要跳过 P0 直接开发。** 设计稿的 8 类愿望字段若不在开工前裁掉，几乎必然被硬编码进代码。
