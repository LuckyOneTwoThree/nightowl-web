## 一、产品演进定位与不可突破边界

### 1.1 现状评估与演进抓手

一期已形成「今晚怎么选 → 本周怎么配 → 赛前止损看球 → 次日防剧透补看」完整骨架。二期不堆砌泛泛的体育资讯，而是聚焦夜猫球迷最痛、传统看球 App 最无解的 4 个断层：

1. **半夜 03:00/04:00 的“全看或全弃”二元困境**：想保核心睡眠又不想错过名局下半场，却没有“下半场切入方案”和“不剧透的局势判断”。
2. **防剧透与“挑集锦”的矛盾**：昨晚 4 场球全打码了，早上只有 10 分钟通勤时间，盲猜点错一场 0-0 闷平非常挫败。
3. **赛前数据“只读不动”**：积分榜能看排名与分差，但缺少“赢了升第几、输了掉去哪”的推演参与感。
4. **双端割裂与长周期无沉淀**：桌面端与 Android 手机端已共享算法与数据，但个人规划/待看清单/已看记录互不相通；看完整个赛季也没有个人战报回顾。

### 1.2 三条铁律（二期一票否决项）

| 铁律 | 规则说明 | 二期延伸约束 |
| :--- | :--- | :--- |
| **红线 1：零云端 / 零账号** | 所有用户状态、账本、手账只存本机（桌面 `127.0.0.1` + `localStorage`，手机 `AsyncStorage`），绝不建中心服务器或账号体系 | 双端同步**只能走一次性局域网配对/离线扫码**；绝不把 `/api/proxy` 暴露到局域网 |
| **红线 2：无源数据零容忍** | 界面禁止出现无明确数据源的指标（xG、控球、首发、出线概率、生理学补觉分钟数等） | 剧情标签必须由真实 ESPN 事件派生；事件缺失时必须降级，绝不猜词；沙盘只能做“1-0/0-0/0-1 确定性推演” |
| **红线 3：防剧透高于一切** | 未揭晓场次的比分、胜负、进球者/红牌归属在防剧透开启时绝不能在文案、角标、通知、导出文件中泄露 | 悬念雷达与剧情心电图**禁止携带主客归属与数字比分**；就算查看本地接口 DTO 也不得下发明文比分给纯摘要视图 |

### 1.3 非目标声明（Explicit Non-Goals）

1. **不做**多用户云端排行榜、社区弹幕、评论区或猜球积分榜。
2. **不做**Android 端锁屏后台高频轮询（受 Android Doze 与续航限制，赛中第 60' 动态悬念雷达以桌面端为主，手机端聚焦“开球前/下半场切入前定时本地提醒”）。
3. **不做**赛季出线概率/蒙特卡洛模拟（无预期实力模型）。
4. **不做**跨公网远程控制或外网穿透转发。

## 三、分模块详细功能需求（FR）

### 模块 M1：无剧透剧情心电图（Drama Meter）· P0

#### 3.1.1 业务场景
用户早上 08:30 打开「晨间补看 (`MorningDigest`)」或开启了防剧透的「已完赛列表」，面前有 3–6 场昨夜已完赛比赛，比分全部被遮罩隐藏。用户需要**在不看到任何比分与胜负结果的前提下**，快速知道哪些场次值得花 10 分钟找集锦/看录像，哪些场次闷平可直接点击揭晓比分跳过。

#### 3.1.2 详细功能需求

| ID | 需求项 | 详细口径与验收标准 |
| :--- | :--- | :--- |
| **FR-M1-01** | **严格无归属事件清洗** | 仅允许使用真实进球、乌龙、红牌、点球、点球未进、关键时间点（分钟数）派生剧情感知；**严禁出现主队/客队名、队徽颜色编码、胜负暗示、`h > a` 等方向性提示**。 |
| **FR-M1-02** | **确定性剧情标签（最多展示 2 个）** | 规则优先级由高到低（仅在真实数据满足条件时输出）：<br>1. `终场悬念 🎭`：存在 `85'+`（或伤停补时）改变领先关系或将分差拉至 `≤ 1` 的进球，**且最终分差 `≤ 1`**；<br>2. `剧本反转 🔄`：依时间轴重放比分，领先方曾发生 `A领先 → B领先` 的反超（仅 `hasEvents === true` 时可判定）；<br>3. `绝平拉锯 ⚖️`：全场领先方被追平次数 `≥ 2`（仅 `hasEvents === true` 时可判定）；<br>4. `进球大战 ⚡`：总进球数 `≥ 4`（有终场比分即可判定，不依赖明细事件）；<br>5. `红点名场面 🟥`：出现红牌或点球（含未进点球）；<br>6. `颗粒无收 💤`：终场确认为 `0-0` 且无红牌。 |
| **FR-M1-03** | **无归属脉冲心电条（90'+ 时间轴）** | 当 `hasEvents === true` 且存在至少 1 条高能事件（进球/乌龙/红牌/点球）时，展示一条细长极简时间条（`0'`–`90'+`），在事件对应分钟刻度上点亮统一中性琥珀色脉冲点；**鼠标悬停/点击不得弹出事件明细与球队名**（防剧透）。 |
| **FR-M1-04** | **摘要缺失诚实降级** | 若当前只有终场比分快照而无 ESPN 事件明细（`hasEvents === false`）：<br>- 仅可依据总进球数判断 `进球大战 ⚡`（`≥ 4` 球）与 `零进球 💤`（`0-0`）；<br>- **严禁**猜测 `剧本反转`、`终场悬念` 或绘制伪造脉冲点；UI 提示「暂无详细时间轴，仅展示赛果烈度」。 |
| **FR-M1-05** | **适用范围控制** | 仅对「已完赛（`isFinished` / ESPN `finished`）且**处于防剧透未揭晓状态**」的场次展示剧情心电图；一旦用户点击「👁️ 揭晓比分」，心电图收起或让位给正常 `RecapTimeline` 明细时间线，避免信息冗余。 |

### 模块 M2：3 分杠杆 · 确定性赛果沙盘（Outcome Sandbox）· P0

#### 3.2.1 业务场景
在强强对话或保级六分战开球前（如阿森纳 vs 曼城），用户在看比赛详情或完整积分榜时，想知道“今晚这 3 分对积分榜格局到底有多大杠杆效应”。

#### 3.2.2 详细功能需求

| ID | 需求项 | 详细口径与验收标准 |
| :--- | :--- | :--- |
| **FR-M2-01** | **入口适用门槛** | 仅对满足以下全部条件的场次显示沙盘条：<br>1. 所属联赛在 `STANDINGS_LEAGUES` 内（`PL`/`PD`/`SA`/`BL`/`FL`，以及 `UCL` 且 `round ≤ 8`；`SCG` 不显示）；<br>2. 场次状态为**未完赛**（`sched` / `live` / `ended_pending`）；若为已完赛且未揭晓场次，为防止反推真实赛果，沙盘基准点仍按开球前截止快照计算或默认禁用；<br>3. 本地已有足够计算积分榜的有效完赛样本。 |
| **FR-M2-02** | **三态推演交互** | 提供互斥切换胶囊：`[基准现状]` / `[若主胜 1-0]` / `[若打平 0-0]` / `[若客胜 0-1]`。再次点击已选假设态可恢复「基准现状」。 |
| **FR-M2-03** | **确定性重算与增量高亮** | 虚拟追加该场结果（严格使用 `1-0` / `0-0` / `0-1` 虚拟比分）并调用现有 `computeStandings` 重算，输出：<br>- 主客双方**实时排名变化**（如 `#4 ↑ #2 (+2)` 或 `#3 ↓ #5 (-2)`）；<br>- 关键分数线关系变化（如“反超榜首 1 分” / “跌出前 4 参考线” / “逃离降级区”）；<br>- 完整积分榜弹窗中同步以琥珀/青/红高亮受影响行。 |
| **FR-M2-04** | **同轮竞争对手护航提示** | 基于同联赛未来 7 天未赛赛程，若发现与主客队**当前排名相差 ≤ 2 位且同处关键分区边界（争冠/前4/欧冠第8与24线/后3）**的另一场对阵，显示一句轻量关联提示：「关联场次：周日 23:30 切尔西赛果将影响本轮前四格局」。 |
| **FR-M2-05** | **合规声明（防误解为概率预测）** | 沙盘结果区固定附小字免责说明：`按本场 1-0 / 0-0 / 0-1 静态推演，其余未赛保持不变 · 简化同分规则`。 |

### 模块 M3：下半场切入策略 + 无剧透“悬念唤醒雷达” · P1

#### 3.3.1 业务场景
面对 03:00 或 04:00 的高代价 S3/S4 场次，用户想用“先睡 5~6 小时，只看最后 30~45 分钟”的折中策略兼顾上班精神与焦点战；并希望桌面端在开球后第 60 分钟自动帮忙判断“这场值不值得叫醒我”。

#### 3.3.2 详细功能需求

| ID | 需求项 | 详细口径与验收标准 |
| :--- | :--- | :--- |
| **FR-M3-01** | **下半场切入时间与睡眠账本试算（双端）** | 当一场比赛满足 `cost > 0` 且开球时间处于 `00:00–05:30` 时，支持用户切换观察模式：**`[看全场]` / `[只看下半场 (60'切入)]`**。<br>- 算法以 `cutInAt = kickoff + 60 分钟`、`endAt = kickoff + 120 分钟` 推导：<br>  1. **赛前可睡窗口**（按用户基准入睡或当前 `now` 至 `cutInAt - 5min`）；<br>  2. **建议起床切入闹钟时刻**（例如 `04:55`）；<br>  3. **相比看全场节省的连续睡眠时段**。<br>- 切换仅作用于展示与个人方案选择，**不篡改引擎底层 `owlIndex` 全场排序口径**。 |
| **FR-M3-02** | **下半场切入闹钟预约（双端本地通知）** | 用户选择「只看下半场」并点击「预约 60' 唤醒」后：<br>- 在 `kickoff + 55min` 注册一条系统级本地定时通知（桌面 Electron `Notification`，手机 `expo-notifications`）；<br>- 通知文案不含比分，写明：`「下半场切入窗口：阿森纳 vs 曼城 即将进入最后 30 分钟」`。 |
| **FR-M3-03** | **无剧透“悬念唤醒雷达”（仅桌面端，需开启开关）** | 用户在睡前可将当日至多 **2 场**尚未开赛的 S3/S4 比赛设为「悬念雷达盯盘」。<br>- 在比赛进入开球后 `55'–65'` 区间时，本地服务端触发受控单次/低频 ESPN live 状态检查；<br>- 判定规则（纯布尔悬念度）：<br>  - **高悬念（值得起）**：`|score.h - score.a| <= 1` **且**（`goal >= 1` 或 `red >= 1` 或 两队积分前 4/德比且平局）；<br>  - **低悬念（继续睡）**：`|score.h - score.a| >= 3`，或非焦点战在第 65' 仍 `0-0` 且无红点事件；<br>  - **未决（兜底如实告知）**：ESPN 抓取失败/无实时比分 → 降级为普通定时提醒`「已到第 60' 切入窗口（暂无实时战况）」`。 |
| **FR-M3-04** | **雷达绝对防剧透隔离** | 雷达推送通知、桌面状态条与本地日志**禁止**出现具体数字（如“目前 1-1”）、禁止出现领先球队名或进球方，只能使用中性状态枚举（`WORTH_WAKING` / `GARBAGE_TIME` / `DULL_DRAW` / `UNAVAILABLE`）。 |

### 模块 M4：观赛情绪印章 + 「我的熬夜赛季账单」 · P1

#### 3.4.1 业务场景
提供轻量、有仪式感的个人看球足迹记录与复盘工具，帮助用户看到自己整个赛季的睡眠付出、主队陪伴率与“熬夜值回票价率”，并可一键导出精美本地图片分享。

#### 3.4.2 详细功能需求

| ID | 需求项 | 详细口径与验收标准 |
| :--- | :--- | :--- |
| **FR-M4-01** | **观赛履历与 1 秒情绪印章** | 在直播播放超过 5 分钟弹窗轻提示、完赛详情页及 `MorningDigest` 点「标记已看」时，可一键记录观赛方式（`直播熬夜` / `半场切入` / `次日集锦`）并附选 1 枚情绪印章（枚举：`神局 🔥` / `揪心 💔` / `催眠 💤` / `惨案 🤦`）及 ≤60 字本地短评。 |
| **FR-M4-02** | **熬夜 ROI 验钞机（本地统计引擎）** | 汇总本地 `WatchedLedger` 与 `fixtures` 完赛真实结果（必须严格受 `reveal` 约束，未揭晓场次不提前剧透进汇总文案或等待揭晓后再入账）：<br>1. **累计出勤统计**：看球总场次、其中 S3/S4 凌晨熬夜场次、累计跨越的夜猫时段分布；<br>2. **“血赚 vs 踩坑”复盘**：熬夜直播的比赛中有几场产出了 `总进球≥3 / 85'+绝杀 / 反转`（血赚），有几场是 `0-0` 闷平（踩坑），并关联显示你的历史平均 ROI；<br>3. **主队陪伴含金量**：主队在你的“深夜出勤场次”里的实际胜率 vs 全季总胜率。 |
| **FR-M4-03** | **本地生成分享长图卡片** | 在桌面端（SVG/Canvas → PNG 下载）与手机端（`react-native-svg` 视图截图保存/系统分享），支持生成一张包含黑金主题、主队队徽、统计数字与“夜猫人设标签（如 `04:00 守夜铁军` / `晨间防剧透专家`，纯由你的真实统计档位映射得出）”的分享图，**全程无网络上传**。 |
| **FR-M4-04** | **数据备份与防丢失** | 将 `WatchedLedger` 纳入 M6 局域网双端同步，并在“设置”提供单个 JSON 导出/导入，防止更换设备或重装清空全季心血。 |

### 模块 M5：跨周魔鬼预警 + 周计划动态日历 + 桌面伴看微控 · P2

#### 3.5.1 详细功能需求

| ID | 需求项 | 详细口径与验收标准 |
| :--- | :--- | :--- |

解决桌面大屏规划 + 床上手机看球 + 早晨通勤标已看的双端状态割裂，全程不依赖云账号。

## 四、非功能性需求与逆向验收准则（NFR）

1. **性能与功耗**：
   - `Drama Meter`、沙盘重算与 `Crunch Radar` 必须在纯函数内单次 `< 5ms` 完成；
   - 悬念唤醒雷达后台轮询必须受 **最大盯盘数 `≤ 2 场` + 仅限 `kickoff+50min ~ +75min` 窗口 + 最短间隔 `≥ 60s`** 三重约束，防止夜间高频请求击穿 ESPN 或拖累本机续航。
2. **双端一致性**：
   - M1/M2/M3(算账)/M4(统计逻辑)/M5(预测/ICS) 全部核心纯函数**必须落于 `src/core/`**，经 `mobile/scripts/sync-shared.mjs` 单向同步至 Android，零分叉。
3. **逆向验收判据（必须写进测试套件）**：
   - 将防剧透打开时，对所有 `Drama Meter` 返回体做正则与键值审计：**不得包含任何连字符比分字符串（如 `\d-\d`）、球队三字码或 `side: 'h'|'a'` 字段**；
   - 将 ESPN `events` 设为空数组（模拟 summary 降级），传 `sc: "2-1"` 时，`Drama Meter` **不得**返回 `剧本反转` 或伪造脉冲点；
   - 在 `127.0.0.1` 常态下向本机局域网 IP 发起 `/api/proxy` 或 `/pair/sync` 请求必须连接失败/拒绝；即使在 120s 配对窗开启期间，向配对端口请求 `/api/proxy` 也**必须返回 404/403**。
